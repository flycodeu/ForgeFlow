# StreamFusion AI · 调研与分析

## 调研要解决的决策

项目不是在几种“视频平台”中选一个名字，而是要决定：视频如何取得与预览、模型与场景如何版本化、连续帧如何成为可解释事件、节点故障怎样恢复，以及哪些数据留在节点、哪些数据进入平台。首条真实流、首个场景和硬件尚未确认，因此外部方案只提供可学习的设计做法，不能代替本项目的运行证据。

## 可借鉴的公开方案

| 资料 | 可学习的部分 | 不能直接移植的部分 |
| --- | --- | --- |
| [Frigate 视频管线](https://docs.frigate.video/frigate/video_pipeline/) | 摄像头输入、解码/采样、检测与快照/录像保存分成明确步骤；主辅码流与事件留存可分别设计 | Frigate 的运动区域触发与 NVR 产品目标不能自动代表本项目场景规则 |
| [MediaMTX 架构](https://mediamtx.org/docs/features/architecture) | 发布者、流路径、多个读取者和控制接口分开，适合评估预览与推理是否复用同一路码流 | 它不执行模型、任务调度和业务事件；是否引入网关要由真实流实验决定 |
| [NVIDIA DeepStream 参考应用](https://docs.nvidia.com/metropolis/deepstream/9.0/text/DS_ref_app_deepstream.html) | 多路输入、推理、追踪和消息输出如何组成节点数据面 | 依赖特定 GPU 软件栈；首场景与硬件基线未定时不把它列为当前实现 |
| [OpenVINO Model Server 文档](https://docs.openvino.ai/2025/model-server/ovms_docs_serving_model.html) | 模型版本、服务端装载与调用契约分离 | 模型服务不负责视频源、场景聚合和节点任务；独立部署只有实测收益才值得增加 |

这些官方资料说明“能怎样设计”，不说明“StreamFusion 已经采用或验证”。本机没有因阅读资料而安装或运行上述组件。

## 当前最重要的取舍

| 决策 | 小闭环候选 | 何时需要升级方案 | 必须取得的证据 |
| --- | --- | --- | --- |
| 视频接入 | Runtime 直接读取一条合法视频流，另行验证浏览器预览 | 多个消费者确需共享流，或协议转换成为明确瓶颈时再评估媒体网关 | 编码、主辅码流、时间戳、断流和两消费者行为 |
| 模型与场景 | 不可变模型版本 + 场景发布版本；任务引用发布版 | 多模型复用与热更新需求出现后再评估独立模型服务 | 同一样本的输出、规则变化与回滚可重复性 |
| 事件生成 | 节点侧把观测聚合为持续事件，平台保存事件和版本引用 | 外部订阅者明确后再建设通知与交付状态 | 重复、漏检、跨重启、证据上传失败样本 |
| 节点资源 | 单路稳定运行并限定队列、重试和进程生命周期 | 多路容量有数据后再比较共享模型、批处理和加速框架 | 指定硬件的吞吐、延迟、显存和故障恢复 |

## 下一次调研应输出什么

取得有授权的真实视频和标注样本，记录场景负责人、设备/编码、模型版本、判断标准、测试环境和原始结果。每个候选方案至少留下“输入、可重复操作、观察值、失败模式、决定和保留问题”。对单条流的测试只能证明该配置，不能外推到生产规模或其他场景。

管理端权限、会话和审计已经是另一条已实现的工程线；具体规则、变更时间与验证证据见同仓 `docs/features/P1-W02/管理功能现状.md`。本页只保留对视频方案选择真正有影响的约束：管理操作须服务端鉴权，任务与事件须带稳定身份和版本，媒体证据不得以大字段进入普通 JSON/关系表。
