# StreamFusion AI · 需求分析

## 首要用户结果

系统最终应让用户从“配置一项视频检测”走到“解释并复核一个事件”。首个验收对象限定为**一条真实视频流、一个场景、一个模型版本**；在样本、设备与业务责任人未确定前，不填入虚构的并发路数、准确率或留存天数。

| 场景 | 必须得到的结果 | 失败时必须可见 | 证据与阶段 |
| --- | --- | --- | --- |
| 管理身份与授权 | 已登录人员只执行获授权的管理操作，关键写入可追查 | 凭据、权限、会话或 IP 防护失败原因可定位 | 管理端已实现；具体回归与负责人状态看功能/验证记录 |
| 登记视频源 | 选定点位和码流，能检查连接及预览条件 | 协议、凭据、网络、编码或源离线不混为“没有数据” | 目标需求；真实设备和字段尚待确认 |
| 发布场景 | 固定模型、输出解释、区域/阈值/持续规则的版本 | 不兼容的模型与规则不能悄悄替换运行任务 | 目标需求；先选首个场景和标注样本 |
| 运行任务 | 能看见期望状态、节点分配、运行实例与最近心跳 | 断流、节点退出、模型加载失败、重复同步有独立状态 | 目标需求；Agent/Runtime 目前只有健康骨架 |
| 查询事件与证据 | 从事件回看点位、时间、场景/模型版、原图或片段 | 事件已登记但媒体未上传须明确显示，不能伪装证据完整 | 目标需求；存储与留存策略待确认 |
| 外部消费结果 | 以稳定事件 ID 和交付状态重试 | 接收失败不重复制造业务事件 | 后续范围；首闭环先实现站内查询 |

## 不应混合的对象

视频源/码流不是任务；模型文件/模型版本不是场景规则；任务配置不是一次运行；逐帧观测不是持续事件；事件元数据不是媒体证据。每一层的 ID、版本和关联要可追踪，修改配置时不能让已有运行或历史证据失去解释基础。部门归属不自动授予 API 权限，页面隐藏也不代替后端鉴权。

## 建议的收敛顺序

1. **先确认输入**：负责人给出首场景、合法视频样本、点位/协议、要识别的业务事实和误报代价。
2. **再证明单路**：记录相同输入的模型输出、时间戳、帧丢弃、断流恢复和显存/时延；得到可复现实验。
3. **连通控制与结果**：任务版本和节点运行对上号；同一事件重复上传可幂等；证据缺失可补偿且状态可见。
4. **最后扩大规模**：在指定硬件和网络下测多路容量、恢复时间与长期稳定性，再决定网关、批处理和通知方案。

该顺序是本次评审建议，不代替负责人确认的交付计划。管理端已经实现的功能继续在功能清单中维护，不重新包装为视频闭环完成。

## 验收输入仍需确认

| 问题 | 最低需要的资料 | 决定后影响 |
| --- | --- | --- |
| 首个检测场景是什么 | 现场责任人、正负样本与误报处置方式 | 事件语义、模型选择、页面内容 |
| 视频能如何访问 | 授权、编码/帧率、网络抖动、主辅码流 | 接入、预览、采样、重连 |
| 资源和时间目标是什么 | 指定节点、GPU/CPU、允许延迟与同时运行路数 | 调度、队列、容量、告警 |
| 证据如何保留 | 原图/标注图/片段需求、访问权、预算与保留期 | 存储、上传、清理、审计 |
| 谁消费事件 | 值班工作流、外部系统、失败补偿方式 | 查询、订阅、幂等交付 |
