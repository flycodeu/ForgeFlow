# StreamFusion AI · 项目背景

## 为什么出现这个项目

项目的起点是一个长期运行的视频分析问题，而不是再做一套账号管理。单段视频上的模型演示只能回答“这一段画面能否识别”；真实场景还需要回答视频源由谁配置、任务在什么节点运行、模型和规则是哪一版、异常中断后是否恢复、告警对应哪段原始证据，以及谁可以查看和处理结果。随着点位、场景和算法增多，这些问题不能只靠独立脚本与文件名维持一致。

这组问题来自项目的公开定位和原始实施指南，是**产品假设与设计动因**；目前没有可引用的现场访谈、点位清单、误报成本或规模指标。因此，本文不把“多路、高并发、实时”写成已确认的验收数字。

## 要让谁完成什么

- 管理人员要知道“谁有权配置和查看哪些内容”，并能追查关键操作。
- 视频业务人员要从视频源与场景配置一项检测任务，看到期望状态和实际运行状态；故障时知道是源、节点、模型还是规则出了问题。
- 值班人员要从事件回到点位、时间、任务、场景版本和原图或片段，能够解释结果从哪里来。
- 节点维护人员要知道任务如何分配、制品如何同步、Worker 如何恢复，且节点故障不能被一个健康接口掩盖。

这些是目标角色与待验证的工作场景，不表示所有界面和链路已交付。

## 方案为什么分成平台、Agent 和 Runtime

平台管理身份、配置、业务状态和事件元数据；Node Agent 协调节点、任务和制品；Runtime 留在节点侧处理拉流、解码、推理和事件生成。这样管理端不搬运逐帧数据，业务规则也不与登录、菜单和数据库事务混在一起。关系库保存可查询的业务记录，媒体证据另行保存；两者通过可追踪的引用关联。

项目先建立 Java/Vue 管理平台及 Python 双进程边界，再完成身份与管理能力，是为以后配置真实视频任务提供受控入口。管理能力的交付过程应记在功能清单、工作记录和验证资料中；它不是项目背景本身。原始指南提出了更完整的视频平台目标，当前仍需通过首个场景收敛。

## 从想法到第一条可信闭环

1. 找到一条获得授权的真实视频流，确定一个检测场景、一个可复现的模型版本和人工可核对样本。
2. 记录视频源与场景配置，建立任务的期望状态、分配版本和一次运行实例。
3. 在节点侧完成拉流、采样、推理和事件聚合；区分瞬时观测与持续业务事件。
4. 保存原图、标注图或片段的证据引用，让页面从事件反查输入、模型、规则、运行和时间。
5. 用断流、重连、重复上报、节点退出和证据上传失败验证恢复与幂等，再扩展多路容量。

这是一条**拟验证路径**，不是当前系统已跑通的业务流程。首个场景、设备协议、允许时延、误报/漏报代价、证据留存和权限范围均须由负责人结合真实环境确认。

## 产品边界与成功判定

首期成功意味着在指定环境中，操作者可以配置、启动、停止并追查一条真实检测任务；事件能够关联到正确的视频时间、算法与规则版本，故障和证据缺失有可见状态，并留下可复现的测试记录。具体性能阈值在场景与硬件确定后再制定。

在线训练、SaaS 多租户计费、复杂 GIS/三维、任意不可信插件执行和同时维护两套等价媒体主链路不属于这条首闭环。外部订阅与通知需在站内事件链真实可靠后再定范围。
