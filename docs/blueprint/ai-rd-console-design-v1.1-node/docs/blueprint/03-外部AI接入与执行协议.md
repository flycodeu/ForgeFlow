# AI 研发控制台：外部 AI 接入与执行协议

版本：v1.1 · 日期：2026-09-18 · 状态：拟定接口契约，尚未实现/联调

> 本文所有 `rd_*` 工具、`/api/v1/*` 业务端点和示例地址均属于待开发的控制台，不是 Codex/Claude 自带功能。本地客户端接入方法依据官方文档核查，具体平台服务仍需开发并验证。

## 1. 接入方式的确定

主路径：**Streamable HTTP MCP → 控制台业务 Service**。

人使用浏览器 REST；外部 AI 使用 MCP；大文件证据使用受限 HTTP 上传。三者共用项目、版本、权限和状态规则。

平台服务示例地址：`http://127.0.0.1:8787`；MCP 示例端点：`http://127.0.0.1:8787/mcp`。这是设计默认值，开工时确认端口是否冲突。

不采用：模拟 AI 点击网页、用浏览器自动化读页面、AI 直接操作控制台数据库、为每个 AI 写一套独立 REST 逻辑、订阅转 API、平台远程启动用户电脑终端。

### 1.1 为什么采用 Node 原生 MCP，而不再引入 Java/Spring 层

平台本身已经需要 Node/TypeScript 前端构建环境，而 MCP 官方 TypeScript SDK v2 直接提供服务端、Streamable HTTP 以及 Fastify 中间件。因此本项目不再为 MCP 单独引入 Spring Boot/Spring AI。[S04][S05]

推荐：同一个 Fastify 应用同时提供 `/api/v1/*`、`/mcp` 和前端静态资源。MCP Tool Handler 与 REST Route 只做协议适配，统一调用 Domain Service。

```text
REST Route ─┐
            ├─ Domain Service ─ Repository ─ SQLite
MCP Tool ───┘
```

不手写 MCP JSON-RPC，不引入模型供应商 SDK，不把 MCP Tool 写成第二套业务系统。只有官方 SDK 在目标客户端真实联调出现不可解决的兼容问题，才评审薄适配器。

### 1.2 本地与远程

首版推荐同机部署：Fastify 监听 `127.0.0.1`，默认端口示例 `8787`。`127.0.0.1` 指当前运行 CLI 的机器；若 Codex/Claude 在 WSL、容器或另一台机器中运行，必须确认实际网络可达性。

远程部署使用 HTTPS 和认证，不把 Bearer Token 发送到公共明文网络。网页 Owner Cookie 与 MCP Token 完全分离。

生产模式可以让 Fastify 直接托管构建后的 Vue 静态文件，因此不需要 Nginx 才能运行；只有 TLS、反代、统一域名等实际需求出现后再加入反向代理。

## 2. 快速接入：控制台完成 S1 后使用

### 2.1 平台准备

负责人在网页完成 Owner 初始化，为 Codex 和 Claude 分别签发 AI Token。Token权限至少包含已授权项目的读取、草稿写入；需要AI创建新项目时再开放“创建项目草稿”。

Token 不是 OpenAI/Anthropic API Key。平台不读取或保存外部 CLI 的模型账号与订阅凭证。

界面生成不含明文凭证的配置片段；实际 Token 放在本地环境变量或相应安全存储里。不要把 Token 写入 Git、截图、聊天或运行日志。

### 2.2 Codex

在用户的 Codex 配置中合并以下片段，不覆盖已有内容。官方支持 HTTP MCP 的 `url` 和 `bearer_token_env_var`。[S01]

```toml
[mcp_servers.rd-console]
url = "http://127.0.0.1:8787/mcp"
bearer_token_env_var = "RD_CONSOLE_CODEX_TOKEN"
```

Windows 用户配置通常位于 `%USERPROFILE%\.codex\config.toml`；存在自定义 Codex home 时按实际位置处理。环境变量需要对启动 Codex 的进程可见，不会自动注入已经运行的进程。

在准备好环境变量之后：

```powershell
codex mcp list
```

随后在目标项目仓库启动 Codex。检查配置存在不等于已经通过读写验收；必须实际调用控制台工具创建/读取测试对象。CLI 参数发生差异时先查看本地 `codex mcp --help`，不要猜一个不存在的参数。[S01]

### 2.3 Claude Code

推荐由控制台生成项目根目录 `.mcp.json` 的待合并片段。Claude Code 官方支持 HTTP server 和 headers 中的环境变量展开。[S12]

```json
{
  "mcpServers": {
    "rd-console": {
      "type": "http",
      "url": "http://127.0.0.1:8787/mcp",
      "headers": {
        "Authorization": "Bearer ${RD_CONSOLE_CLAUDE_TOKEN}"
      }
    }
  }
}
```

先让启动进程获得 `RD_CONSOLE_CLAUDE_TOKEN`，再运行 Claude Code 并批准这个项目 MCP。检查：

```powershell
claude mcp list
claude mcp get rd-console
```

会话中可用 `/mcp` 检查连接。[S12]

需要通过 CLI 创建项目配置时，PowerShell 可使用以下形式；单引号保留环境变量占位符，交给 Claude 读取配置时展开：

```powershell
claude mcp add --scope project --transport http rd-console http://127.0.0.1:8787/mcp --header 'Authorization: Bearer ${RD_CONSOLE_CLAUDE_TOKEN}'
```

已有同名配置时先检查并合并，不盲目重复添加或删除其他服务。也可以使用客户端提供的 user scope 做跨项目接入，但必须按实际版本验证凭证加载；项目级配置是本方案最小可复现接入方式。[S12]

### 2.4 接入后的第一条指令

```text
请连接 rd-console。
先列出我有权限访问的项目，不修改任何项目。
随后创建名为 MCP联调 的草稿项目，写入一句测试需求，
再按返回的项目ID和规格版本读取，确认写入和读取一致。
不要批准设计，不创建业务代码，不修改其他项目。
```

S1 验收后归档此测试项目，不需要把测试数据长期混在生产项目列表里。

### 2.5 代码执行的实际前提

MCP 接上控制台，不代表 AI 已进入正确代码目录。编码前必须在外部 CLI 中核对当前工作目录、仓库标识、Git 基线和授权路径。

平台知道 `repository_id=REPO-01`，不代表平台可以操作客户端的 `D:\Projects\demo`。本地项目绑定配置负责这种映射；服务端只存仓库身份和相对代码引用。

普通网页版 AI 是否可访问本机服务取决于其实际连接能力。本方案首要验证目标只承诺本地 Codex 和 Claude Code，不把其他客户端的接入写成已完成。

## 3. 角色和允许操作

| 行为 | Owner网页 | AI Client | 后续采集器 |
|---|---:|---:|---:|
| 创建/修改项目草稿 | 是 | 有范围权限时可以 | 否 |
| 写设计新修订、Task草稿、Case草稿 | 是 | 可以 | 否 |
| 请求设计评审、提出问题 | 是 | 可以 | 否 |
| 批准设计基线 | 是 | 否 | 否 |
| 授予/撤销执行授权 | 是 | 否 | 否 |
| 获取授权、启动Run | 查看/管理 | 有效授权下可以 | 仅被委派采集 |
| 提交变更、测试报告、问题 | 是 | 可以，注明来源 | 可以，注明来源 |
| 确认任务完成、人工验收 | 是 | 否 | 否 |
| 批准交付、删除历史 | 交付可；历史受保护 | 否 | 否 |

AI 读写草稿是一种低风险工作权限，不需要每保存一段文案都人工确认。它也不允许绕过已批准设计直接实施代码。

通过 `actorId`、`approvedBy` 或 `provenance=CI_VERIFIED` 等客户端自填字段，不能改变请求者权限和证据来源。身份与可信级别由服务端认证入口决定。

## 4. MCP 工具目录

工具按阶段暴露。尚未实现的工具不出现在 tools/list 中，不返回模拟成功。以下字段使用 snake_case；REST可使用既定JSON命名风格，但语义映射须唯一。

| 工具 | 阶段 | 必需输入/条件 | 返回与作用 |
|---|---|---|---|
| rd_project_list | S1 | query可选、cursor/limit | 有权限的项目摘要，不带全量设计 |
| rd_project_create | S1 | project_key、name、project_type、brief、idempotency_key | 草稿项目ID；不批准任何内容 |
| rd_outline_read | S1/S2 | project_id、scope_ref可选、cursor | 模块/Feature/阶段摘要；精确ID映射 |
| rd_spec_read | S1 | spec_id、revision_id或明确head/approved、section_ids、cursor | 正文分段、版本、哈希、未返回内容 |
| rd_spec_save | S1 | 新规格的owner/kind，或spec_id+expected_head_revision_id；正文/章节；幂等键 | 新修订ID；永不覆盖批准内容 |
| rd_plan_apply | S2 | project_id、expected_plan_version、operations、idempotency_key | 有限批量草稿写入和临时ID映射 |
| rd_review_request | S2 | target_type、target_id、candidate_version/hash | 创建待人评审项，不等于批准 |
| rd_task_context | S2/S3 | project_id、task_id或feature_id | 当前任务、批准依据、授权、限制、代码和测试入口 |
| rd_run_start | S3 | task_id、grant_id、expected_task_version、workspace_snapshot、idempotency_key | 原子领取后的run_id；重新校验授权 |
| rd_run_event | S3 | run_id、client_seq、kind、message、details | 追加阶段事件/阻塞说明；非任意状态修改 |
| rd_evidence_prepare | S3 | run_id、文件元信息、预期大小/哈希、idempotency_key | 同源限时上传目标、evidence_id、限制 |
| rd_check_record | S3/S4 | run_id、candidate_ref、profile、case_refs、status、结果和证据引用 | 技术结果记录；S3为基础报告，S4完整用例关联 |
| rd_run_submit | S3 | run_id、结果摘要、文件清单、候选版本、验证/证据/问题引用、幂等键 | SUBMITTED结果，后续任务仍未授权 |
| rd_issue_write | S2/S3 | project_id、issue_id可选、expected_version、type、影响和描述 | 创建/补充Bug、决策或变更；不直接关闭 |
| rd_history_read | S2/S3 | project_id、target_ref、cursor | 修订、评审、授权、Run、验收历史 |

### 4.1 rd_plan_apply 的边界

支持的 operation 固定为创建/更新模块草稿、Feature草稿、Task草稿和关系草稿。规格内容通过 rd_spec_save 保存，验收条目与对应规格修订一起绑定。

不得接受任意对象类型和任意字段 patch。`status=ACCEPTED`、`approved=true`、`grant.create` 等字段直接拒绝。更新已授权任务定义必须进入新的草稿/变更，不修改活跃授权快照。

默认单批最多25项和明确请求大小；关联先用temp_key，在同一事务中解析。返回 created/updated/id_mapping 和新的 plan_version。失败返回失败原因，不伪造整体完成。

### 4.2 rd_spec_save 的两种合法模式

创建：owner_ref + kind + title + markdown，expected_head为空；相同逻辑对象重复创建通过幂等键识别。

修订：spec_id + expected_head_revision_id + 新正文或受控章节替换。章节替换必须带原章节哈希；不接受“随便把第一个类似句子替换掉”的模糊操作。

每次返回新revision_id、hash、base_revision_id及保存结果。AI下一次修改必须基于该返回版本。

### 4.3 错误语义

| 错误码 | 含义 | AI动作 |
|---|---|---|
| NOT_AUTHENTICATED | 凭证缺失/无效 | 停止，不尝试猜Token |
| PROJECT_FORBIDDEN | 项目不在权限范围 | 报告，不搜索绕过 |
| VERSION_CONFLICT | 旧版本写入 | 读新版本和差异后重新提出修改 |
| EXECUTION_NOT_AUTHORIZED | 未授权代码执行 | 只报告，不自行创建授权 |
| DEPENDENCY_UNSATISFIED | 必要条件未满足 | 提问题/建议最小补齐任务 |
| BASELINE_STALE | 授权依据失效 | 停止并请求重新确认 |
| WORKSPACE_MISMATCH | 仓库/基线不匹配 | 核对本地路径，不自动reset |
| ACTIVE_RUN_EXISTS | 已有有效Run | 读取其状态，不重复执行 |
| EVIDENCE_INCOMPLETE | 缺材料/未上传完成 | 补材料，不改为通过 |
| SCOPE_VIOLATION | 业务或文件范围越界 | 提交问题，不直接推进 |
| CAPABILITY_NOT_READY | 当前版本未支持 | 不编造能力，不自动另造一套系统 |
| IDEMPOTENCY_CONFLICT | 同幂等键用于不同内容 | 改正调用逻辑，不重复写入 |

REST使用相应HTTP状态，例如401/403/409/422。MCP协议与工具错误通过SDK的规范响应表达；工具业务失败返回可解析的错误码和trace_id，不把一个字符串“ok”当成成功。HTTP认证失败应在MCP边界前拦截。

## 6. 项目绑定配置

本地仓库可以保存一份小型绑定文件，示例：

```yaml
# .rd/project.yaml：只定位，不保存动态状态
schema_version: 1
server: http://127.0.0.1:8787
project_id: PA
repository_id: REPO-01
mcp_server_name: rd-console
rules: AGENTS.md
```

不保存 Token、currentTask、approved、progress。绝对本机路径如有需要放到被 Git 忽略的 `.rd/local.yaml`，且服务器不依赖它打开文件。

允许未来同项目多个仓库；首版先支持一个主要仓库，数据结构保留repository_id。不要为了“未来多仓库”立刻实现代码同步和跨仓库提交事务。

## 7. 执行上下文示例

以下为结构示意，所有占位版本必须由服务端实际记录替换：

```yaml
schema_version: 1
project:
  id: PA
  name: 项目A
  type: WEB
feature:
  id: F-001
  name: 用户管理基础能力
  lifecycle: IMPLEMENTING
task:
  id: F-001-T02
  definition_version: 3
  name: 后端用户启停规则及测试
  state: AUTHORIZED
context:
  baseline_id: BL-008
  digest: '<上下文摘要>'
  complete: true
  required_references:
    - spec_id: SPEC-013
      revision_id: REV-007
      sections: [scope, requirements, failure-recovery, acceptance]
  omitted_required_references: []
authorization:
  grant_id: G-018
  valid_at_snapshot: true
  claim_required: true
  expires_at: '<真实有效期>'
repository:
  id: REPO-01
  expected_base_commit: '<真实代码SHA>'
allowed_paths:
  - src/modules/user/**
  - test/user/**
forbidden_paths:
  - src/ui/**
  - 'migrations/**'
  - AGENTS.md
  - CLAUDE.md
  - .rd/**
operations:
  commit: false
  push: false
  merge: false
  deploy: false
verification:
  profiles: [app-build, user-module-tests]
  acceptance_refs: [AC-U-03]
next_task:
  id: F-001-T03
  authorized: false
stop_after: SUBMIT_RESULT
```

`valid_at_snapshot` 仅表示快照当时有效；run_start 必须重新检查，防止取上下文到执行之间授权变化。不能把旧YAML当成长期通行证。

服务端实际应把必需规则正文或可按ID读取的精确引用一并返回。AI不得依据名称猜内容，也不能只读摘要就跳过明确要求的关键条款。

## 8. 两类 AI 工作流程

### 8.1 从零规划

```text
人：提出项目目标与约束
→ rd_project_list：查重和定位
→ rd_project_create：必要时建草稿项目
→ rd_spec_save：保存需求分析/架构候选/技术选择草稿
→ rd_plan_apply：创建模块、Feature和阶段草稿
→ rd_spec_save：细化当前迭代的重要功能与验收条件
→ rd_issue_write：记录真正阻塞的未决项
→ rd_review_request：提交评审
→ 停止，等待人确认
```

初期可以没有Git仓库；这不阻止需求规划。禁止因为“整个项目最终需要数据库”就先创建全部迁移和业务代码。

规划必须包含需求边界、架构理由、首版范围和可验证成果。远期模块只设计到边界，不一次生成数百页未确认实现细节。

### 8.2 已批准任务实施

```text
读本地绑定与规则
→ rd_task_context：定位唯一批准任务
→ 读取必要指定版本
→ 检查本地仓库、Git状态、工具环境
→ rd_run_start：领取有效任务
→ 用外部AI自带文件/终端工具实施
→ rd_run_event：上报关键阶段
→ 本地运行批准的验证
→ 上传必要报告/补丁/截图
→ rd_check_record：记录结果和来源
→ rd_run_submit：提交成果
→ 停止，不进入下一任务
```

没有对应任务时可以提出Task草稿，不允许自行授权后继续。项目描述中写“自动完成所有功能”也不能覆盖控制台规定的当前范围。

### 8.3 任务内修复与超范围变化

当前测试发现自身实现错误，可以在本任务批准范围内修复并再次执行测试。若需要改数据库、公共API、全局安全规则或新增未批准依赖，则上报Issue，停止相关实施。

不得为了让测试通过删除用例、降低断言、修改业务规则或把未执行标成通过。确属测试定义错误，创建设计/用例修订，等待人确认。

## 9. Run 提交格式

以下为记录示例，不代表真实运行结果：

```json
{
  "run_id": "RUN-00128",
  "idempotency_key": "RUN-00128-submit-1",
  "outcome": "SUCCESS",
  "summary": "按批准规格完成用户启停规则及对应测试",
  "workspace": {
    "repository_id": "REPO-01",
    "base_commit": "<实际基线SHA>",
    "head_commit": "<实际HEAD-SHA>",
    "dirty": true,
    "patch_evidence_id": "EV-001",
    "patch_sha256": "<实际摘要>"
  },
  "changed_files": [
    {
      "path": "src/modules/user/user.service.ts",
      "change_type": "MODIFIED",
      "source": "CLIENT_REPORTED"
    }
  ],
  "verification_refs": ["CHECK-003"],
  "evidence_refs": ["EV-001", "EV-002"],
  "issue_refs": [],
  "unexecuted_checks": [
    {"name": "前端交互", "reason": "不属于当前授权范围"}
  ],

}
```

服务端不能仅凭 `outcome=SUCCESS` 确认任务，也不能把 changed_files 自报认定为完整实际 Diff。审查包或采集器可增强检查；无此能力时页面明确标注来源。

提交不包括 `feature_state=ACCEPTED`、`task_state=CONFIRMED`、`approved_by` 等可越权字段。下一步只是建议。

## 10. 验证配置和结果格式

任务引用批准的验证配置，配置定义在项目规格或Git中明确的权威文件。包含命令、工作目录、超时、依赖环境和报告位置。它是执行要求，不是平台远程Shell入口。

```yaml
profile_id: user-module-tests
revision: 2
repository_id: REPO-01
cwd: .
platform: windows
executable: pnpm.cmd
args: [vitest, run, test/user]
timeout_seconds: 180
expected_reports:
  - reports/vitest/*.xml
```

实际配置按项目技术栈确认。不同操作系统可有多个profile；AI不能把Windows命令直接当Linux可执行，也不能因为目标类不存在就静默换成一个容易通过的测试。

结果保存至少：profile版本、实际命令、实际cwd、代码候选、时间、退出码、测试计数、报告引用和未覆盖项。没有执行记录的状态为NOT_RUN/BLOCKED，不能凭模型推测。

CI可信来源只能由登记的CI认证入口授予。AI把普通报告文件上传过来，来源仍是AI_REPORTED。报告的哈希证明文件是否变化，不证明报告内容真实。

## 11. 大文件证据传输

不要把完整日志、截图Base64或整个仓库塞到MCP上下文。

```text
AI申请受限上传
→ 平台返回同源上传地址、evidence_id、大小/类型限制
→ AI使用本地已有文件上传能力提交真实字节
→ 服务端核对并保存
→ 上传完成后引用evidence_id写入CheckRun/Run
```

返回的地址只能指向本控制台预期origin，不允许工具参数指定任意外部回传地址。服务器不根据AI提供的本地路径读取文件。

上传和业务提交不是一个跨文件系统数据库原子事务：文件先进入暂存区，校验后标记STORED；Run只允许引用已完成证据。失败可重试；未被引用的过期暂存文件由维护任务清理。

证据访问继续按项目权限校验，不能把目录作为无鉴权静态网站暴露。敏感内容需要在本地与服务端两侧检查，不能认为哈希或HTTPS会自动脱敏。

## 12. 重试、并发和中断

| 情况 | 规则 |
|---|---|
| 写入响应丢失 | 用同幂等键重试，先确认结果是否已存在 |
| 同键内容变化 | 冲突，不返回旧成功掩盖差异 |
| 两个AI改同一设计 | 预期版本校验；后者读新版本再修订 |
| 两个AI领同一任务 | 数据库事务保证唯一有效Run |
| 两任务写同仓库 | 初版默认串行；后续再加范围冲突检测 |
| CLI中断 | 记录未完成；重开后查已有Run，不重复领取 |
| 服务中断 | 保存本地结果，停止新的受控写入；恢复后对账 |
| 授权撤销 | 不再开始/继续新的平台许可动作；已有材料可归档但不可正常推进 |
| 长时间无事件 | 显示stale/未知，不假定进程已停止或任务失败 |

MCP服务不负责强制杀死用户本地CLI进程。审批撤销不等于本地Shell已停止，界面必须把两者分开说明。

## 13. AGENTS.md 与 CLAUDE.md 的关系

共同执行规则只写一份，控制在日常可读范围。Codex通过项目AGENTS.md加载规则；Claude Code使用CLAUDE.md，并可以引用共享内容。[S02][S03]

建议：

```text
AGENTS.md             共同规则 + 控制台绑定入口
CLAUDE.md             薄适配入口，引用共同规则
.rd/project.yaml      项目和仓库定位
```

不要为每个功能生成一套超长Agent规则。当前范围来自task_context，不从旧规则文件推断。

工具层权限、平台审批和模型提示词各负其责。Claude官方明确区分项目说明和强制配置；本方案不把Markdown指令当安全边界。[S03]

## 14. 接入与协议验收清单

成功接入必须同时证明：客户端发现工具、认证生效、创建/读取一致、版本冲突生效、AI不能审批、请求可审计。

完整执行必须再证明：指定任务领取、仓库基线核对、实际代码/测试、结果写回、等待人确认、不能自动继续下一任务。

记录客户端版本、平台版本、MCP传输方式、操作系统和测试时间；不能把一次工具列表截图当成所有版本兼容证明。
