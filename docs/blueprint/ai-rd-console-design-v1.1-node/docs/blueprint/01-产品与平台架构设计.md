# AI 研发控制台：产品与平台架构设计

版本：v1.1 · 日期：2026-09-18 · 状态：Node/TypeScript 架构重构稿，待人工评审，未实施

## 1. 产品定义与目标

### 1.1 一句话定义

一个由人管理、由外部 AI 读写和执行的研发控制台，把需求、设计、模块、任务、代码结果、测试、验收和版本组织成可追踪流程。

核心使用方式：

> 我在 Codex 中说明“项目 A 增加用户管理”。Codex 从控制台读取项目，提出功能设计和实施计划，写入待评审版本。人评审并批准当前任务后，Codex 在项目本地仓库实施、测试和提交记录。控制台展示结果，人决定是否继续。

控制台不自行思考、生成需求或写代码。上述生成行为由用户当前打开的外部 AI 完成。网页可以提供“复制规划指令”和“复制执行指令”，初版不设置暗中调用模型的“自动开发”按钮。

### 1.2 必须解决的问题

| 当前问题 | 产品能力 | 可观察结果 |
|---|---|---|
| 文档和状态散落在目录里 | 项目树、Feature 工作台、结构化设计索引 | 不通过猜文件名定位功能 |
| 每次评审重读全文 | 设计修订、差异、待决事项、版本基线 | 先看变化和影响，再按需读原文 |
| AI 不知道下一步 | 当前授权与任务上下文 | 没有唯一授权就停止 |
| AI 写了代码但没有记录 | Run、文件变更、测试与问题写回 | 每次实施都能追溯输入和产出 |
| 测试通过被当成全部完成 | 技术验证、人工验收、交付分离 | 页面不会只有一个 DONE |
| 新会话重复解释 | MCP 读取明确上下文 | AI 从实际记录恢复，不依赖聊天记忆 |
| 不同项目需要不同设计 | 模板化章节、任务类型、验证类型 | Godot 不被强制生成 Controller 或数据库表 |

### 1.3 v1.0 包含和不包含

包含：多项目、模块/功能树、需求与设计版本、设计评审、任务授权、外部 AI 接入、执行记录、测试结果、人工验收、问题与变更、交付记录、Markdown 导入导出、基础检索和备份恢复。

不包含：内置大模型聊天、模型 API 聚合、接管 Codex/Claude 登录、无人值守多 Agent 调度、远程终端、任意 Shell 执行服务、浏览器 IDE、流程拖拽设计器、组织权限矩阵、工时统计、完整 Git 托管、向量库、Kubernetes。

外部 AI 自带的文件和命令执行能力继续由其本身提供；平台只提供业务上下文和受控业务操作。

## 2. 架构与部署边界

### 2.1 总体架构

```text
人类负责人 ── 浏览器 ── REST API ───────────────┐
                                                │
本地 Codex / Claude Code ── HTTP MCP ──────────┤
                                                ▼
                               Node.js / TypeScript 单体服务
                     ┌──────────────┬──────────────┐
                     │ REST / Auth  │ MCP / Context│
                     └──────┬───────┴──────┬───────┘
                            │              │
                     同一组 Domain Service / Policy
                            │
                  SQLite + 本地 Evidence 目录

本地 Codex / Claude Code ── 自带文件/终端工具 ── 业务项目仓库
                                                  │
                                          Git / 构建 / 测试
                                                  │
                              MCP 写回结果 + 证据上传
```

开发环境可以运行两个进程：Vite 开发服务器和 Node API。生产环境构建前端后，由同一个 Fastify 服务托管静态前端，因此默认部署形态只需要 **一个 Node 进程 + 一个 SQLite 文件 + 一个证据目录**。不要求 Docker；需要远程部署时再用 Compose 或系统服务托管。

REST Route 和 MCP Tool Handler 必须调用同一组 Domain Service。状态机、事务、版本校验、审批权限和幂等只实现一次，MCP 层不复制业务逻辑。

### 2.2 三个明确边界

**管理边界：**平台负责记录、批准、拒绝、显示和关联。

**执行边界：**代码和测试在外部 AI 所在的本地项目环境执行。平台初版不运行这些命令，不必拥有业务仓库的可写挂载。

**信任边界：**外部 AI 上报“测试通过”是来源明确的报告，不自动变成平台独立验证。后续采集器和 CI 可以增强证据，但不能倒填早期记录的信任等级。

### 2.3 推荐技术栈

| 层次 | 推荐 | 选择理由 |
|---|---|---|
| Runtime | Node.js 24 LTS + TypeScript | 与 MCP 官方 TypeScript SDK 同生态；单机部署轻量 |
| 包管理 | pnpm workspace | Web、Server、共享契约统一锁版本 |
| HTTP 服务 | Fastify 5 | 低开销、成熟插件体系、适合 REST/SSE；MCP 官方 SDK 提供 Fastify 中间件 |
| MCP | `@modelcontextprotocol/server` + `@modelcontextprotocol/fastify` | 直接使用官方 TypeScript SDK v2，不增加 Spring/Java 中间层 |
| 参数/契约 | Zod v4 | MCP 工具和共享 DTO/输入校验统一定义；REST 适配方式在 S0 锁定 |
| 数据库 | SQLite（首版） | “我 + AI / 少量开发者”写并发低，部署、备份、恢复成本最低 |
| 数据访问 | Drizzle ORM + `better-sqlite3` | 类型化 SQL、迁移简单；避免重型 ORM |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus | 保持熟悉栈，适合管理控制台 |
| 状态管理 | Vue Router + Pinia（只在实际跨页状态出现时使用） | 不为简单页面预建复杂全局状态 |
| Diff | 首版文本 Diff；需要代码审查体验时引入 Monaco Diff | 不把浏览器 IDE 当首版目标 |
| 页面更新 | 普通请求 + 按需刷新；Run 事件成熟后增加 SSE | 不先做 WebSocket/消息队列 |
| 证据 | 本地文件目录 + DB 索引 | 首版不部署 MinIO；保留 EvidenceStorage 抽象即可 |
| 测试 | Vitest + Fastify inject；前端 Vitest；关键 UI 使用 Playwright | 一套单元/接口测试 + 少量 E2E，避免堆框架 |
| 部署 | 单 Node 进程 + SQLite；可选 systemd/Windows 服务/Docker | 最低运维成本 |

截至 2026-09-18，Node.js 24 为 LTS；MCP 官方 TypeScript SDK v2 已对应 2026-07-28 协议并提供 Fastify/Node Streamable HTTP 中间件。Fastify 5 为当前主版本。具体 npm 小版本仍在 S0 用锁文件固定，不在文档里追逐 `latest`。[S04][S05][S06]

**SQLite 的选择不是“系统永远只能单机”。**它是首版部署策略。平台出现多人长期并发写、独立服务扩容或数据库远程高可用需求后，再评估 PostgreSQL/MySQL。首版不为这个未来场景提前维护第二套数据库。

Node 24 自带 `node:sqlite` 当前仍处于 Release Candidate 稳定级别，因此首版优先使用成熟的 `better-sqlite3`；待内置 SQLite 稳定后可单独评估替换。Drizzle 同时支持 `better-sqlite3` 和 `node:sqlite`。[S07][S08]

### 2.4 服务端内部模块

使用“模块化单体”，按业务域组织，不采用 NestJS 式大量装饰器、Controller/Service/Repository 模板，也不建设微服务：

```text
workspace       项目、模块、Feature、仓库关系
specification   需求/架构/功能规格、修订、差异、基线
review          待审、评论、人工决定
execution       任务定义、授权、Run、事件
quality         用例、技术验证、证据、人工验收
change          Bug、未决事项、变更影响
release         发布范围、候选产物、交付
integration     MCP、上下文、导入导出
security        Owner、AI Client、Token
```

每个模块通常只保留：`routes.ts / service.ts / repository.ts / schemas.ts` 中真正需要的文件。HTTP Route 和 MCP Tool 只做协议适配；Service 负责业务规则；Repository 负责持久化。没有复用价值时不创建抽象基类、接口 + Impl 双层、通用 Factory 或事件总线。

## 3. 项目对象与粒度

### 3.1 主层级

```text
Project 项目
└── Module 模块
    └── Feature 功能增量
        └── Task 可授权工作单元
```

里程碑和 Release 是交付视图，引用 Feature，而不是创建另一份功能树。第一版不强制单独创建 Work Package；可以用里程碑分组满足阶段管理。后续确有跨模块工作包需求时再增加实体。

示例：

```text
PA 项目 A
├── MOD-01 项目基础
├── MOD-02 系统管理
│   ├── F-001 用户管理基础能力
│   ├── F-002 角色管理基础能力
│   └── F-003 菜单管理基础能力
└── MOD-03 设备接入
```

Feature 是一次可以完成验收的功能增量，不是永远重开的“用户管理总桶”。后续批量导入可新建 Feature，并关联原功能。

### 3.2 ID

| 对象 | 展示 ID | 说明 |
|---|---|---|
| Project | PA | 项目内命名空间 |
| Module | MOD-02 | 项目内唯一 |
| Feature | F-003 | 项目内唯一，不编码可变父级 |
| Task | F-003-T02 | 所属 Feature 内的工作单元 |
| 规格 | SPEC-013 / revision 7 | 内容对象和修订分离 |
| 基线 | BL-008 | 一组确定版本的批准依据 |
| Run | RUN-00128 | 一次实际执行 |
| 用例 | AC-M-05 | 稳定逻辑 ID，记录具体定义版本 |
| Issue | ISS-0009 | Bug、决策项或变更 |
| Release | REL-0.1.0 | 交付版本 |

数据库采用内部 ID，不依赖显示编号做关联。对外返回 ID 字符串，避免 JavaScript 大整数精度问题。保留旧编号 `P1-W01-E` 为别名，别名在项目内唯一；重名必须让用户选择，不能 AI 猜测。

### 3.3 Task 的合理粒度

按独立目标、风险、依赖和“这里是否需要暂停”划分。例如：

```text
设计与验收定义
→ 后端业务实现及测试
→ 前端交互及测试
→ 集成验证和必要修复
```

需要控制某个实现边界时再拆成独立任务。普通文件、类、DTO、数据访问层不自动成为任务；每个用例也不自动成为一个 Task。

任务必须有限：一个批准目标、一组输入、一组允许范围、一组可验证产出、一个停止点。新发现的附带优化只进入建议或变更草稿。

## 4. 需求和设计怎样保存

### 4.1 内容对象，不是文件夹

平台提供版本化规格对象 `Spec`。每个规格有类型、所属项目/模块/Feature、正文、稳定章节 ID、修订历史和引用。

项目级规格建议合并为三类，不强制生成三份文档：

| 类型 | 内容 |
|---|---|
| 项目需求与范围 | 使用者、目标、场景、包含/不包含、约束、成功条件 |
| 架构与技术选择 | 系统边界、组件职责、技术决策、数据流、部署、风险 |
| 交付与验证策略 | 首版范围、里程碑、验证方式、验收与发布要求 |

模块级只有存在共享规则时才需要独立规格。普通 Feature 默认一个规格，章节如下：

```text
scope             范围、非范围
requirements      功能规则及需求 ID
interaction       页面/交互/状态
implementation    必要的实现约束与代码入口
contracts         API/数据/资源引用
failure-recovery  异常、并发、恢复
dependencies      已确认和未确认依赖
acceptance        可执行验收条件
open-decisions    未决事项
```

章节可以因项目类型裁剪。没有数据库的游戏不出现空的数据库设计；存在存档时使用存档格式和兼容性设计。

### 4.2 内容格式

正文保留 Markdown，界面按稳定章节折叠和定位；章节目录可以由受控标记解析。初版不实现复杂块数据库、任意嵌套编辑器或在线协同算法。

结构化保存的不是全部句子，而是：身份、版本、关系、Task、Case、Issue、Review 和状态。叙述性规则保留 Markdown。二者通过稳定 ID 连接。

### 4.3 需求追踪，避免为了填表而填表

每条重要需求使用如 `REQ-U-03` 的 ID；每个验收项引用其覆盖需求。任务引用涉及的需求或功能条目。实际变更和测试证据再引用任务/用例。

```text
REQ-U-03 禁用用户后不能继续使用受保护功能
      ↓
Feature F-001 / Spec revision 7
      ↓
Task F-001-T02
      ↓
Run + 代码结果
      ↓
AC-U-03 + CheckRun
      ↓
人工验收 + Release
```

不强制每一行代码映射一个需求。代码位置关联用于导航和影响分析；“文件关联存在”不证明需求已经实现。

### 4.4 修订、评审与批准

每次有效保存产生一个不可变修订；保存时带 `expectedHeadRevisionId`。内容相同可返回 no-op，不产生无意义版本。两个客户端基于旧版本保存时，后者获得冲突响应，必须先读取差异。

评审比较“上一个批准版本”和“这次候选版本”，显示：变化章节、完整 Diff、关联任务/用例、未决项和建议影响。AI 摘要只是导航，原始 Diff 始终可展开。

批准针对不可变 Baseline，其中固定相关项目架构、模块规则、Feature 设计、验收定义版本。任务授权另固定任务定义快照和代码基线。

新草稿不自动撤销旧批准。新版本获批时由系统计算已知引用影响，并让人确认需要暂停/重新验证的范围；无法确定的影响标记待确认，不能悄悄沿用旧授权。

“当前已批准版本”和“最新草稿”同时显示。人工批准不能被一个 AI 上传的 `approved=true` 字段代替。

## 5. 页面与交互设计

### 5.1 六个一级入口

| 页面 | 默认内容 | 关键动作 |
|---|---|---|
| 项目总览 | 项目树、实施/验收/交付三类进度、阻塞、待我处理 | 创建/切换项目，进入功能 |
| 项目/Feature 工作台 | 概览、设计、任务、变更、测试、验收、历史 | 按需展开详细资料 |
| 评审中心 | 待设计批准、待任务确认、待决问题、待业务验收 | 看差异、批准、退回 |
| 执行记录 | 当前 Run、最后上报时间、阶段事件、文件和验证 | 查看真实记录，报告中断 |
| 版本与交付 | 发布范围、候选版本、证据、交付结果 | 验收和交付确认 |
| AI 接入与设置 | MCP 地址、Token、项目范围、配置片段、导入导出 | 接入 CLI，不管理模型账号 |

“需求新建”属于项目/Feature 工作台，不另外做一套聊天收件箱。输入简述保存为需求草稿，再复制带项目 ID 的规划指令给外部 AI。

### 5.2 项目树

树节点显示名称、生命周期、必要计数。点击 Module 展示共享设计和 Feature 汇总；点击 Feature 展示其工作台。

树按需加载；列表分页；不要一次向浏览器返回所有规格正文和历史 Run。搜索优先精确 ID、别名、标题和标签，随后检索正文。中文检索可先用有限范围全文/包含查询，再依据实际规模评估索引。

### 5.3 Feature 默认概览

```text
菜单管理基础能力  F-003（旧编号 P1-W01-E）
设计：待评审     实施：未核验     测试：未执行
当前可执行任务：无

本功能做什么：维护导航配置和已注册页面入口
不做什么：外链、任意组件路径、API 权限授予

待你决定：保护入口清单
待核实依赖：认证快照、首个路由消费者、已有库升级
本次变化：只读最新修订相对上次评审的差异

[功能设计] [任务] [代码结果] [测试] [人工验收] [历史]
```

此处“未核验”表示尚未检查真实仓库。导入的说明声称未实施，可以作为来源备注，但不能靠文档自动确认实际代码状态。

### 5.4 评审交互

设计评审：先显示变化和待决项，提供展开原文、逐章节评论、要求修改和批准基线。

实施评审：展示批准目标、实际改动、范围检查、测试来源、未执行项、未解决问题。用户可以“确认本次结果并授权下一项”，后台仍分别生成确认记录和新授权。

人工验收：按用例或验收组操作；显示候选构建和条件。通过/失败/不适用必须有相应结论。严重缺证据不能一键全部通过。

### 5.5 运行中进度的真实含义

平台能直接观察到 MCP 调用和证据上传；本地 CLI 的读文件、思考和 Shell 行为只有主动上报或采集器接入后才可显示。初版阶段事件是 `读取上下文 / 开始实施 / 开始验证 / 结果已提交`，不伪造逐文件实时轨迹。

页面始终区分“平台接收到”“客户端报告”和“独立验证”。没有新上报时显示最后联系时间和“当前情况未知”，不能自称 AI 正在执行某条命令。Token 用量不可获取时显示未提供，不估算为精确数。

## 6. 生命周期、任务和执行状态

### 6.1 Feature 生命周期

| 状态 | 含义 | 转换条件 |
|---|---|---|
| DRAFT | 范围草稿/待设计 | 创建对象 |
| DESIGNING | 正在设计 | 发生设计工作，尚无批准基线 |
| DESIGN_REVIEW | 待评审 | 候选规格已提交评审 |
| READY | 设计已批准、待实施 | 人批准必要基线 |
| IMPLEMENTING | 已有实施任务启动 | 有有效授权的 Run 开始 |
| VERIFYING | 整体技术验证中 | 必要实施任务已确认 |
| ACCEPTANCE_PENDING | 待人工业务验收 | 必要技术验证满足策略，无阻断问题 |
| ACCEPTED | 业务已验收 | 人确认绑定候选版本的验收 |
| DELIVERED | 已交付 | 交付范围和产物满足已批准条件 |

生命周期是服务端规则维护的投影；不提供 AI 任意设置该字段的接口。阻塞是附加信息，不把 IMPLEMENTING 覆盖成无法恢复原阶段的单一 BLOCKED。

### 6.2 Task 状态

`PLANNED → AUTHORIZED → RUNNING → SUBMITTED → CONFIRMED`

`SUBMITTED` 可以包含成功、失败或部分结果，不代表完成。人要求修改后，任务返回 PLANNED，补充新授权和新 Run；旧 Run 不覆盖。CANCELLED 是明确取消的终止状态。

设计任务不要求已经有设计批准，但权限只允许生成草稿。代码任务必须有批准基线和当前授权。小项目可以一次批准一个窄的“后端实现与测试”任务，不要求每个方法都审批。

### 6.3 Run 与结果

Run 状态：`RUNNING / SUBMITTED / INTERRUPTED / CANCELLED`。

Run 结果：`SUCCESS / FAILED / PARTIAL / BLOCKED`。执行过程中结果为空。失去联系只标记 stale，不等于 FAILED；人或客户端通过明确恢复/终止操作处理。

一个 Task 同时最多一个有效 Run。启动和提交使用幂等键及事务校验；第二个客户端不能同时领取。首版可限制同一项目只运行一个写代码 Run，使冲突管理保持简单。

### 6.4 四类人类决定

1. 批准设计基线。
2. 批准当前执行范围。
3. 确认任务成果。
4. 人工业务验收/交付确认。

界面可合并操作，但记录不能混淆。AI 凭证不具备这些权限；即使直接调用人类 REST 端点也必须被拒绝。

## 7. 授权与上下文

### 7.1 Task 定义

必填：目标、任务类型、所属范围、输入引用、依赖、产出、停止条件。

代码任务另外必填：仓库、允许/禁止修改范围、测试要求、需要覆盖的验收条目、基线约束。允许范围既包含业务范围，也包含路径范围。

示例：

```yaml
id: F-001-T02
kind: IMPLEMENTATION
objective: 实现用户启停业务规则及对应测试
baseline_id: BL-008
allowed_behavior:
  - 实现已批准的用户启停与会话失效规则
allowed_paths:
  - src/modules/user/**
  - test/user/**
forbidden_paths:
  - src/modules/auth/**
  - migrations/**
forbidden_behavior:
  - 新增角色权限体系
  - 修改公共身份协议
verification_profiles: [app-build, user-module-tests]
acceptance_refs: [AC-U-03]
stop_after: SUBMIT_RESULT
```

以上是平台记录/导出示意，不要求用户手写 YAML。

### 7.2 授权记录

授权固定：Task 定义版本、Baseline、允许范围、禁止范围、仓库、有效期、是否允许提交/推送/合并/部署、授权人和时间。

授权执行范围不得超出已批准设计与任务定义。需要扩大时重新提议，由人确认。默认不允许 push、merge、deploy；commit 可单独授权。

完成提交、撤销、期限到达或基线冲突均不能继续领取后续任务。MCP 写回不可用时先保存本地结果；不继续下一任务。

### 7.3 上下文分层

| 层 | 内容 | 加载方式 |
|---|---|---|
| 项目概要 | 范围、架构摘要、当前阶段、规范入口 | 小型摘要 |
| 当前目标 | Feature/Task、有效授权、待决项 | 一次定位 |
| 精确依据 | 批准规格章节、契约引用、依赖 | 按任务组装 |
| 代码范围 | 仓库 ID、相对路径、符号/测试入口 | 本地 AI 按需读 |
| 最近事实 | 上次 Run、未解决问题、证据有效性 | 摘要和按需展开 |

上下文返回必须包含 `baselineId / taskDefinitionVersion / authorizationId / requiredReferences / omittedReferences`。必要依据缺失时不返回 ready=true。不能为了减少 token 静默截断安全规则或验收条件。

读取代码范围可以按必要性扩展；修改范围不能自主扩大。项目文档和导入内容作为数据，不得覆盖平台授权规则。

## 8. Source of Truth 与导出

| 事实 | 权威位置 | 派生副本 |
|---|---|---|
| 原生需求、设计、模块、任务定义 | 平台数据库中的规格/对象版本 | Markdown/JSON 导出 |
| 当前状态、审批、授权、Run | 平台数据库 | UI、上下文快照、历史报告 |
| 代码与代码历史 | 对应 Git 仓库 | 上传的审查片段/补丁 |
| 可执行 API 契约和数据库 migration | Git 中指定文件 | 平台显示引用及版本 |
| 真实部署环境/迁移执行结果 | 该环境/部署记录 | 平台证据和关联 |
| 用例定义 | 对应批准规格修订的结构化用例快照 | 展示表格 |
| 测试和验收结论 | CheckRun/Acceptance 记录 | 进度和报告 |
| 原始证据 | 受管文件存储 | 数据库中的摘要、哈希和索引 |

平台里的 API 说明不能与 Git 中的 OpenAPI 同时独立维护同一契约字段。项目可暂时把契约作为规格草稿；正式采用契约文件后登记其 authoritative source，不允许两边互相覆盖。

批准后可生成便携快照：

```text
exports/PA/BL-008/
├── project.json
├── manifest.json
├── specifications.md
└── acceptance.json
```

可通过本地 AI 按已批准目录保存到仓库，再由有权限的一方提交。平台不因“导出”自动拥有 Git commit/push 权限。快照导出失败不伪造成功；基线保持批准事实，导出状态另记 PENDING/FAILED/EXPORTED。

导出不是完整备份。数据库、证据目录和必要运行配置均需备份；Token 不以明文导出，恢复后建议重新签发。恢复演练验证设计历史、批准记录和证据仍可关联。

## 9. 数据模型与约束

### 9.1 逐阶段创建，而不是首轮建齐所有表

以下是目标逻辑模型，实体随功能阶段落库。字段为开发设计依据，不是本轮生成可执行 SQL。业务项目自己的库表设计属于被管理规格，不应混入控制台数据库。

| 表/实体 | 主要字段 | 关键约束 |
|---|---|---|
| rd_project | id, project_key, name, project_type, scope_summary, version, archived_at | key 唯一；归档不删历史 |
| rd_unit | id, project_id, type(MODULE/FEATURE), parent_id, code, aliases, title, lifecycle, weight, version | 同项目父子；只有固定两层；禁止环 |
| rd_repository | id, project_id, repo_key, remote_url, kind | 不以服务器绝对路径作为唯一身份 |
| rd_spec | id, project_id, owner_type, owner_id, kind, head_revision_id, approved_revision_id | head 和 approved 分离 |
| rd_spec_revision | id, spec_id, revision_no, base_revision_id, markdown, sections, content_hash, author_id, created_at | 正文不可覆盖；spec+revision 唯一 |
| rd_baseline | id, project_id, scope_ref, references_json, content_hash, created_by, created_at | references 固定精确版本；同项目校验 |
| rd_review | id, target_type, target_id, candidate_hash, status, decision, actor_id, comment, created_at | 人类决定从服务端身份获取；决定不可覆盖 |
| rd_task | id, project_id, feature_id或项目作用域, code, kind, definition_json, definition_version, state, weight, version | 授权后定义冻结；草稿修改需乐观锁 |
| rd_grant | id, task_id, baseline_id, task_snapshot, effective_scope, repo_id, capabilities, expires_at, revoked_at, actor_id | 仅人签发；任务/项目/基线一致 |
| rd_run | id, task_id, grant_id, client_id, state, outcome, repo_snapshot, result_json, started_at, submitted_at, idempotency_key | 每任务最多一个有效 Run；提交幂等 |
| rd_event | id, project_id, target_ref, run_id, kind, actor_id, client_seq, payload, created_at | 追加事件；同 Run 序号去重 |
| rd_case | id, project_id, case_key, spec_revision_id, requirement_refs, type, steps, expected, required | case_key+spec_revision 唯一；批准后定义不可改 |
| rd_check_run | id, run_id, candidate_ref, case_snapshot, profile_snapshot, environment, status, provenance, results, evidence_refs | 同候选、同用例版本才能汇总 |
| rd_evidence | id, project_id, run_id, storage_key, filename, mime, size, hash, provenance, state | 只能绑定同项目；服务端校验大小和哈希 |
| rd_acceptance | id, target_ref, baseline_id, candidate_ref, case_results, conclusion, actor_id, created_at | 仅人确认；历史不可覆盖 |
| rd_issue | id, project_id, feature_id, type, severity, status, source_ref, affected_refs, description, resolution_ref, version | AI 可提问题/建议；不能擅自关闭阻断问题 |
| rd_release | id, project_id, version_name, scope_snapshot, candidate_refs, acceptance_refs, delivery_status, decision_ref | 发布范围固定；交付由人批准 |
| rd_link | id, project_id, source_ref, relation, target_ref | 关系类型白名单；同项目及目标存在检查 |
| rd_actor | id, type(OWNER/AI_CLIENT/后续COLLECTOR), display_name, login_name, password_hash(仅Owner), disabled_at | 初版单 Owner；AI 不可升级为 Owner；密码只存安全摘要 |
| rd_token | id, actor_id, token_hash, prefix, scopes, project_scope, expires_at, revoked_at | 只存摘要；仅首次显示明文 |

核心关系使用明确外键或等效事务校验；`rd_link` 只用于需求/代码导航和影响关系，不替代全部结构化关联。

任务定义、基线引用等小型快照可用 JSON；经常筛选的状态、归属和时间必须是明确列。禁止把全库做成无约束 EAV/万能 JSON 表。

### 9.2 并发与事务

- 草稿保存、任务定义修改携带 expectedVersion；冲突返回 409 和当前版本，不静默覆盖。
- 批准操作检查候选版本是否仍是人看到的版本；防止浏览器旧页面批准新内容。
- 启动 Run 在事务内检查授权、状态、依赖并占用任务；多客户端竞争只能一方成功。
- 提交结果和状态转换在同一数据库事务中完成；证据先上传完成再引用，缺失附件不能伪造已收齐。
- Idempotency-Key 绑定调用者、端点/工具、请求体摘要；同键同内容返回原结果，同键异内容返回冲突。
- 授权撤销后仍可接收正在执行任务的最终说明和已有证据，但标记 revoked_context，不允许按正常完成推进。
- 不能仅使用内存锁维护关键互斥，否则重启后容易破坏规则。首版单实例也用数据库条件更新/事务保证。

### 9.3 删除和审计

业务对象优先归档。已批准修订、审批、Run、验收和交付记录不提供 AI 删除接口。普通草稿可由人取消；清理过期原始日志遵循保留策略，保留结果摘要和删除记录，不制造可点击但不存在的证据链接。

## 10. 代码关联、Diff 和仓库边界

平台保存仓库 ID、代码基线、结果 Commit 或补丁摘要、路径和必要片段。代码正文仍属于 Git。

本地 Windows 路径只保存在本机绑定配置；服务端在 Linux 上也不能直接打开 `D:\Projects\demo`。没有远程 Git 集成时，由本地 AI/采集器上传审查包，或者在浏览器手工上传。

Diff 必须相对本次 Run 开始时确认的基线，覆盖：已经提交的变化、暂存/未暂存变化、新文件、删除、重命名、二进制资源和文件模式变化。只运行一次普通 `git diff` 可能漏掉已提交/已暂存/未跟踪内容，不能把空输出当成没有变更。[S09]

检测到已有用户未提交修改时，不默认清理。首次版本建议要求清晰的干净基线，或由人明确接受带有原始差异摘要的工作区。无法区分来源时停止，而不是把所有本地变化都归给 AI。

每个 Run 不强制创建 worktree。单人串行可使用一个 Feature 分支；并行或需要隔离工作文件时再使用 worktree。Git worktree 共享仓库相关元数据，不是操作系统安全沙箱；删除它之前必须保存并核对未提交结果。[S09]

## 11. 测试与验收

### 11.1 分层结果

```text
实施产物提交
→ 任务成果确认
→ Feature 技术验证
→ 人工业务验收
→ 指定版本交付
```

Task 自身必须运行其要求的测试；后续 Feature 技术验证检查多部分集成。并不是先写完全部代码才考虑测试。

每个 CheckRun 保存：命令或测试配置快照、工作目录标识、代码/构建版本、环境、用例版本、开始结束时间、退出码、通过/失败/跳过数、证据来源、原始报告引用。

### 11.2 状态与证据来源分别保存

测试状态：NOT_RUN / RUNNING / PASS / FAIL / BLOCKED / SKIPPED。

来源：

| provenance | 含义 |
|---|---|
| AI_REPORTED | 外部 AI 上报；即使附报告也不能冒充独立执行器 |
| COLLECTOR_RECORDED | 本地辅助工具记录命令、退出码和文件摘要 |
| CI_VERIFIED | 经登记的独立 CI 结果和签名/可信回调核实 |
| HUMAN_REVIEWED | 人审查并确认相应材料；不是把手测伪装成自动测试 |

采集器与 AI 在同一账号、同一可写机器上时不构成防恶意伪造的强信任边界。来源分层用于说明证据形成方式，不宣称绝对真实性。

默认技术门禁要求关键验证通过且存在报告、版本一致、未覆盖项明确。仅 AI_REPORTED 的关键结果进入“待证据确认”，人确认或独立验证后再推进。可以按项目配置允许的证据策略，但必须清楚展示策略，不把弱证据隐藏。

SKIPPED 和 N/A 不等于 PASS。确需豁免，由人记录理由、影响和期限；不能把测试计数全部改为通过。

### 11.3 三个验收视角

Feature 验收：这次功能增量是否满足规则。

Module 验收：多个 Feature 之间的共享权限、数据、交互是否一致。

Release/工作包验收：本次承诺的整体业务链和交付目标是否成立。

一次演示可复用证据覆盖多个视角，不强制重复开会或重复写报告。

### 11.4 候选版本变化

通过结果只适用于所记录的规格和代码/构建。修改代码、合并冲突、改变依赖或重新构建后，先判断受影响验证，再重跑必要项。证据仍留在历史，但当前视图标记 STALE，不静默继承。

人工验收绑定确定的候选 Commit/构建/资源包。无 Commit 的早期审查可以使用不可变补丁摘要，但最终交付应有可识别和可复现的版本。

## 12. 问题、返工与持续扩展

Issue 分三类即可：BUG、DECISION、CHANGE。不要每条聊天意见都创建独立工单。

Bug：关联发现时的 Run、需求/用例和候选版本；修复有明确 Task，补充回归用例，原问题记录不覆盖。

Decision：用于会阻止设计、实施或验收的未决项；必须写清阻塞哪个范围。菜单保护清单可能只阻塞保护路径验收，不应无理由阻塞所有菜单树读取开发。

Change：已批准范围或设计调整。先生成新草稿，列出影响，再批准相关基线和任务。不要靠修改测试期望把已批准规则改掉。

可以在同一个已授权任务内修复自身引入的问题并重跑测试，只要没有改变批准目标、范围和契约。超出范围或涉及公共设计时停止并提出变更。

## 13. 进度计算

项目默认显示三类进度：工程实施、人工验收、交付。设计用“批准/待评审/未完成/待核实”显示，必要时展示必需章节完成数，不显示 AI 凭空填写的 90%。

Feature 内实施进度：已确认实施 Task 权重 / 已承诺实施 Task 总权重。权重用简单的 1/2/3/5，批准计划时固定。

项目实施进度：按 Feature 范围权重加权汇总。人工验收进度按已 ACCEPTED 的 Feature 权重计算；交付按 DELIVERED 计算。Module 和 Release 视图引用同一 Feature，不重复计数。

新增范围必须记录分母变化。未展开的远期功能显示“未估算”；没有足够基线时展示数量和状态，而非虚构百分比。零任务、全部不适用等情况返回 N/A，不能除零或默认 100%。

自动验证同时展示覆盖率和运行结果，例如“必需场景已覆盖 8/10；本次测试 24/24 通过”，不能用测试文件条数代表需求覆盖。

## 14. 旧 Markdown 迁移

推荐逐个活动 Feature 迁移，不一次清洗整个文档库：

```text
读取已有文件/粘贴正文
→ 保留原文、文件路径与哈希
→ AI 提取范围/能力/用例/依赖/未决项草稿
→ 人查看导入差异
→ 选择转为平台原生规格
→ 原文件改为来源归档或只读导出
```

初版不自动执行 Markdown 中的指令，不访问任意链接，不扫描全磁盘。导入的链接仅作为待解析引用。

来源模式明确区分：

- ARCHIVED_SOURCE：原文备查，不参与当前状态判断。
- EXTERNAL_REFERENCE：尚未迁移，平台只展示其引用/版本；修改权仍在原位置。
- NATIVE_SPEC：经确认迁入，后续在平台生成修订；原文件不再双向编辑。

你提供的菜单管理材料可以提取 M-01～M-08、验收场景和依赖。它说明本轮只做设计、业务验收未执行；因此导入初始状态为待评审和验收未执行。真实代码状态仍需一次仓库核验，未读取的 B/C/D 关联资料标记待核实，不能自动认证其已完成。

## 15. 通用项目模板

模板只是章节、检查项和建议任务类型，不是代码生成器，更不是可执行插件市场。首版使用固定、可版本化的模板定义；后续允许编辑模板，但不允许运行模板里的任意脚本。

| 内容 | Web 项目 | Godot 游戏 | 通用工具 |
|---|---|---|---|
| 需求 | 用户与业务流程 | 玩家目标与核心循环 | 使用场景与输入输出 |
| 架构 | 前后端、模块、数据 | 场景/节点/脚本/资源职责 | 程序模块与集成 |
| 数据设计 | 数据库/缓存/契约 | 配置、资源、存档版本 | 文件格式或本地数据 |
| 实施 | Backend/Frontend 等 | Gameplay/UI/Asset 等 | Core/UI/Integration |
| 自动验证 | 单元/接口/集成 | 脚本、数据、存档与可自动化场景 | 单元/兼容/集成 |
| 人工验收 | 业务操作 | 试玩、手感、视觉/音效 | 实际工作流程 |
| 交付 | 构建包与部署 | 导出包与目标平台 | 安装包/脚本/可执行文件 |

Godot 官方支持命令行运行和导出等能力，但引擎启动成功不代表游戏玩法和画面通过验收；自动验证配置必须针对具体项目，手感和视觉保留人工验收。[S10]

## 16. 安全与非功能要求

### 16.1 最小认证

Owner 通过本地安装初始化；首次创建不能开放给任意公网访问者。网页会话使用安全 Cookie/CSRF 防护。AI 使用独立 Token，按项目限制读取、草稿写入和执行写回权限。

`project:draft:create` 是单独能力，允许用户授权的规划客户端创建新项目草稿；它不赋予批准、删除、部署或修改所有其他项目的权限。

MCP 官方 SDK 只提供协议与传输能力，平台仍必须自己实现业务认证、项目作用域和工具权限。MCP 端点启用 Token 校验、Host/Origin 防护、请求限额和工具级权限，不因为“在本机”就裸露写接口。Streamable HTTP 的安全要求以当前 MCP 协议为准。[S05][S11]

### 16.2 不暴露的能力

认证后的请求主体由服务端显式传入 Domain Service；异步调用时也必须正确传递并隔离主体，不能依赖可被并发请求串用的全局可变变量，更不能接受工具参数伪造主体。

没有通用 `execute_sql`、`shell_exec`、`read_any_file`、`set_status`、`grant_self` 工具。MCP 工具参数不能注入审批人、任意服务器路径或外部回调地址。

上传限制大小、数量和 MIME；存储键由服务端生成；拒绝路径穿越。日志、Diff、报告进行秘密检查与脱敏，禁止默认上传 `.env`、私钥、完整用户数据和凭证。

Markdown 渲染禁用或清理危险 HTML；外链明确提示；代码和文档内容不作为高权限指令。

### 16.3 本地外部 AI 的硬边界

平台可以强制执行自己的 API 权限、版本和状态规则。外部 CLI 拥有操作系统文件权限时，仍可能在不调用平台的情况下修改本地代码。AGENTS.md、CLAUDE.md、MCP 授权和路径检查不能形成绝对阻断。[S02][S03]

需要更强隔离时，后续使用独立工作目录、受限工具/系统账号、沙箱和受保护合并/部署流程。本项目 v1.1 只承诺“流程可控、越界可检查、结果有来源”，不承诺不可绕过的本地安全执行环境。

### 16.4 建议验收负载，不是实测性能

建立种子数据：10 个项目、每项目 30 个模块/300 个 Feature、总计 10,000 个任务与执行记录。在选定部署机上测分页、树加载、详情和上下文接口，记录 CPU/内存/数据库规模。

建议页面首屏和普通上下文请求目标为秒级；具体阈值在 S0 以机器与数据量确认。不得把这个目标写成已达成的资源/性能结论。

### 16.5 可靠性

备份要覆盖数据库和证据目录；做一次恢复验收。导出和大报告处理可以使用单体内受限后台任务，但不要因此引入独立队列集群。重启后待完成任务从数据库恢复状态，不能只靠内存集合。

## 18. 从新需求到交付的完整例子

### 18.1 新 Web 系统

人描述设备台账系统目标 → 外部 AI 创建项目草稿 → 写需求/架构候选/模块树/首版 Feature/阶段计划 → 提出待决项 → 人批准首版范围和关键架构。

远期模块只给边界和依赖，当前迭代的用户管理才细化接口、数据、业务规则、任务和验收。避免一次为 50 个模块生成无人能评审的细节。

用户管理设计获批 → 人批准后端任务 → AI 获取上下文、核对本地仓库并启动 Run → 编码、测试、写回报告和 Diff → 人确认 → 批准前端 → 集成验证 → 人业务验收 → 交付。

### 18.2 Godot 游戏

人描述“2D 采集经营原型” → AI 创建 GAME_GODOT 项目 → 规划核心循环、输入、场景、资源/存档、模块与首次可玩版本 → 人批准范围。

`背包基础` Feature：规则包括堆叠上限、满包反馈和存档恢复；任务可以是数据模型、交互界面、自动验证和试玩。代码范围是 GDScript/场景/资源目录，不生成 Web 后端专属层。

AI 通过同样的 MCP 接口读写；本地用 Godot 工具执行项目约定检查，截图/录屏和导出包作为证据。试玩手感由人验收，自动测试不能替代。

### 18.3 已交付后继续扩展

已有背包基础已交付 → 新建 `背包排序与分类` 增量 → 引用原有设计和存档约束 → 产生新批准基线和任务 → 回归原有行为 → 发布新版本。

旧版本的批准、Run、验收和交付历史始终可查，不用把旧 Feature 的“已完成”抹掉来容纳所有未来变化。

## 19. 开工判断

满足以下条件才进入 S1：确认系统边界、事实来源、候选技术栈、第一阶段真实 MCP 目标和不变量；其余详细实现按阶段评审。

本方案不要求先开发所有数据表、所有流程和所有页面。开发顺序和每阶段停止点见 [02-分阶段开发与验收计划](02-分阶段开发与验收计划.md)。协议和官方技术依据见 [03-外部AI接入与执行协议](03-外部AI接入与执行协议.md)。
