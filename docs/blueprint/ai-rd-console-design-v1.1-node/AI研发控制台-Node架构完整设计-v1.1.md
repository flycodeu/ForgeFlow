# AI 研发控制台：设计文档包

版本：v1.1（Node/TypeScript 架构重构稿）  
日期：2026-09-18  
状态：仅完成方案设计；平台代码、MCP 服务、测试与验收均未执行。  
工作名称：AI 研发控制台（暂定产品名 ForgeFlow）；示例项目代号 `RDC`，MCP 服务名 `rd-console`。名称不影响协议，可在开工前调整。

## 1. 这次确定的系统边界

本项目是“外部 AI 可读写的研发项目系统”，不是内置聊天机器人、远程 IDE 或自主多 Agent 开发平台。

- 人在网页里看项目、评审差异、批准任务、验收成果。
- 本地 Codex / Claude Code 通过 MCP 读取和维护项目资料。
- AI 使用自己已有的本地文件/终端能力，在业务项目仓库编写代码、运行测试。
- 平台接收版本、进度、问题、Diff、测试报告和验收证据，不默认启动 AI、不代管模型订阅、不远程运行任意命令。
- 同一套系统管理 Web 后台、工具软件、Godot 游戏等项目；具体设计章节和验证方式由轻量项目模板决定。

**平台数据库保存项目规格和流程事实；Git 保存代码、契约、迁移及导出的批准快照。导出文件不是第二套可双向编辑的状态库。**

## 3. 第一次怎样使用

1. 把文档包放到控制台项目仓库的 `docs/blueprint/`，保留相对文件名。
2. 把 `04` 中的“平台开发启动提示词”交给 Codex / Claude Code。
3. 第一轮只执行 S0 的设计核对和阶段拆分；不自动创建整套业务代码。
4. 人确认 S0 后，批准 S1 当前任务。S1 必须尽早打通真实 MCP 读写，而不是先做完漂亮界面。
5. S3 完成后，才能用平台正式授权外部 AI 编码并提交执行记录。S4 补齐严格技术验证、业务验收和交付。

平台尚未可用期间，使用本包的阶段清单记录启动工作；不要伪造“已通过平台批准”。平台闭环可用后，再一次性导入自己的项目资料，注明哪些批准是人工导入的历史事实。

## 4. 必须保持的十个不变量

| 编号 | 不变量 |
|---|---|
| I-01 | 没有有效执行授权，不允许把草稿规划理解为代码实施授权。 |
| I-02 | AI 身份不能批准设计、授予执行权限、确认人工验收或批准交付。 |
| I-03 | 已批准规格的内容不可覆盖；修改生成新版本。 |
| I-04 | Task 提交、Task 确认、Feature 验收、Release 交付分别记录。 |
| I-05 | 一个 Task 同时最多一个有效 Run；提交必须幂等。 |
| I-06 | 测试结果绑定实际代码/构建、用例版本和环境；未执行不等于通过。 |
| I-07 | AI 上报、采集器记录、独立 CI 验证和人工确认的证据来源不得混淆。 |
| I-08 | 页面进度来自结构化事实；未知状态不能自动换成 0% 或 100%。 |
| I-09 | Markdown/Git 导出只读；修改导出文件不会悄悄覆盖平台批准版本。 |
| I-10 | MCP 和规则文件不等于本地操作系统沙箱；平台不能保证控制有完整本地权限的外部 CLI。 |

## 5. 方案中的“已经核实”与“尚未执行”

已核实：官方文档支持 Codex / Claude Code 连接 MCP；MCP 官方 TypeScript SDK v2 已提供 Node.js、Streamable HTTP 与 Fastify 中间件；Node.js 24 当前为 LTS。数据库首版建议使用 SQLite + better-sqlite3/Drizzle，避免为了个人/少量并发场景额外维护 MySQL 服务。官方依据见 `03` 文末。

尚未执行：本项目 MCP 联调、Node 依赖构建、SQLite 迁移、界面实现、CLI 真实写回、性能和安全测试。因此所有端点、工具名、数据表和运行示例都是本项目的拟定契约，不是已部署能力。

你此前提供的菜单管理正文可作为导入测试材料；其关联文档和仓库没有在本轮实际读取，不能据此宣布代码已完成或任何验收通过。

## 6. 阅读负担控制

这套文档是控制台的开发蓝图，不是以后每次 AI 都要全量加载的上下文。日常执行只读：项目概要、当前任务、被引用的批准设计段落、必要代码入口和对应验证要求。

功能详情页默认显示摘要、当前任务、待你决策、设计差异与最新证据。全文和历史材料按需展开。

# AI 研发控制台：产品与平台架构设计

版本：v1.1 · 日期：2026-09-18 · 状态：Node/TypeScript 架构重构稿，待人工评审，未实施

## 1. 产品定义与目标

### 1.1 一句话定义

一个由人管理、由外部 AI 读写和执行的研发控制台，把需求、设计、模块、任务、代码结果、测试、验收和版本组织成可追踪流程。

核心使用方式：

> 我在 Codex 中说明“项目 A 增加用户管理”。Codex 从控制台读取项目，提出功能设计和实施计划，写入待评审版本。人评审并批准当前任务后，Codex 在项目本地仓库实施、测试和提交记录。控制台展示结果，人决定是否继续。

控制台不自行思考、生成需求或写代码。上述生成行为由用户当前打开的外部 AI 完成。网页可以提供“复制规划指令”和“复制执行指令”，初版不设置暗中调用模型的“自动开发”按钮。

### 1.2 必须解决的问题

| 当前问题 | 产品能力 | 可观察结果 |
|---|---|---|
| 文档和状态散落在目录里 | 项目树、Feature 工作台、结构化设计索引 | 不通过猜文件名定位功能 |
| 每次评审重读全文 | 设计修订、差异、待决事项、版本基线 | 先看变化和影响，再按需读原文 |
| AI 不知道下一步 | 当前授权与任务上下文 | 没有唯一授权就停止 |
| AI 写了代码但没有记录 | Run、文件变更、测试与问题写回 | 每次实施都能追溯输入和产出 |
| 测试通过被当成全部完成 | 技术验证、人工验收、交付分离 | 页面不会只有一个 DONE |
| 新会话重复解释 | MCP 读取明确上下文 | AI 从实际记录恢复，不依赖聊天记忆 |
| 不同项目需要不同设计 | 模板化章节、任务类型、验证类型 | Godot 不被强制生成 Controller 或数据库表 |

### 1.3 v1.0 包含和不包含

包含：多项目、模块/功能树、需求与设计版本、设计评审、任务授权、外部 AI 接入、执行记录、测试结果、人工验收、问题与变更、交付记录、Markdown 导入导出、基础检索和备份恢复。

不包含：内置大模型聊天、模型 API 聚合、接管 Codex/Claude 登录、无人值守多 Agent 调度、远程终端、任意 Shell 执行服务、浏览器 IDE、流程拖拽设计器、组织权限矩阵、工时统计、完整 Git 托管、向量库、Kubernetes。

外部 AI 自带的文件和命令执行能力继续由其本身提供；平台只提供业务上下文和受控业务操作。

## 2. 架构与部署边界

### 2.1 总体架构

```text
人类负责人 ── 浏览器 ── REST API ───────────────┐
                                                │
本地 Codex / Claude Code ── HTTP MCP ──────────┤
                                                ▼
                               Node.js / TypeScript 单体服务
                     ┌──────────────┬──────────────┐
                     │ REST / Auth  │ MCP / Context│
                     └──────┬───────┴──────┬───────┘
                            │              │
                     同一组 Domain Service / Policy
                            │
                  SQLite + 本地 Evidence 目录

本地 Codex / Claude Code ── 自带文件/终端工具 ── 业务项目仓库
                                                  │
                                          Git / 构建 / 测试
                                                  │
                              MCP 写回结果 + 证据上传
```

开发环境可以运行两个进程：Vite 开发服务器和 Node API。生产环境构建前端后，由同一个 Fastify 服务托管静态前端，因此默认部署形态只需要 **一个 Node 进程 + 一个 SQLite 文件 + 一个证据目录**。不要求 Docker；需要远程部署时再用 Compose 或系统服务托管。

REST Route 和 MCP Tool Handler 必须调用同一组 Domain Service。状态机、事务、版本校验、审批权限和幂等只实现一次，MCP 层不复制业务逻辑。

### 2.2 三个明确边界

**管理边界：**平台负责记录、批准、拒绝、显示和关联。

**执行边界：**代码和测试在外部 AI 所在的本地项目环境执行。平台初版不运行这些命令，不必拥有业务仓库的可写挂载。

**信任边界：**外部 AI 上报“测试通过”是来源明确的报告，不自动变成平台独立验证。后续采集器和 CI 可以增强证据，但不能倒填早期记录的信任等级。

### 2.3 推荐技术栈

| 层次 | 推荐 | 选择理由 |
|---|---|---|
| Runtime | Node.js 24 LTS + TypeScript | 与 MCP 官方 TypeScript SDK 同生态；单机部署轻量 |
| 包管理 | pnpm workspace | Web、Server、共享契约统一锁版本 |
| HTTP 服务 | Fastify 5 | 低开销、成熟插件体系、适合 REST/SSE；MCP 官方 SDK 提供 Fastify 中间件 |
| MCP | `@modelcontextprotocol/server` + `@modelcontextprotocol/fastify` | 直接使用官方 TypeScript SDK v2，不增加 Spring/Java 中间层 |
| 参数/契约 | Zod v4 | MCP 工具和共享 DTO/输入校验统一定义；REST 适配方式在 S0 锁定 |
| 数据库 | SQLite（首版） | “我 + AI / 少量开发者”写并发低，部署、备份、恢复成本最低 |
| 数据访问 | Drizzle ORM + `better-sqlite3` | 类型化 SQL、迁移简单；避免重型 ORM |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus | 保持熟悉栈，适合管理控制台 |
| 状态管理 | Vue Router + Pinia（只在实际跨页状态出现时使用） | 不为简单页面预建复杂全局状态 |
| Diff | 首版文本 Diff；需要代码审查体验时引入 Monaco Diff | 不把浏览器 IDE 当首版目标 |
| 页面更新 | 普通请求 + 按需刷新；Run 事件成熟后增加 SSE | 不先做 WebSocket/消息队列 |
| 证据 | 本地文件目录 + DB 索引 | 首版不部署 MinIO；保留 EvidenceStorage 抽象即可 |
| 测试 | Vitest + Fastify inject；前端 Vitest；关键 UI 使用 Playwright | 一套单元/接口测试 + 少量 E2E，避免堆框架 |
| 部署 | 单 Node 进程 + SQLite；可选 systemd/Windows 服务/Docker | 最低运维成本 |

截至 2026-09-18，Node.js 24 为 LTS；MCP 官方 TypeScript SDK v2 已对应 2026-07-28 协议并提供 Fastify/Node Streamable HTTP 中间件。Fastify 5 为当前主版本。具体 npm 小版本仍在 S0 用锁文件固定，不在文档里追逐 `latest`。[S04][S05][S06]

**SQLite 的选择不是“系统永远只能单机”。**它是首版部署策略。平台出现多人长期并发写、独立服务扩容或数据库远程高可用需求后，再评估 PostgreSQL/MySQL。首版不为这个未来场景提前维护第二套数据库。

Node 24 自带 `node:sqlite` 当前仍处于 Release Candidate 稳定级别，因此首版优先使用成熟的 `better-sqlite3`；待内置 SQLite 稳定后可单独评估替换。Drizzle 同时支持 `better-sqlite3` 和 `node:sqlite`。[S07][S08]

### 2.4 服务端内部模块

使用“模块化单体”，按业务域组织，不采用 NestJS 式大量装饰器、Controller/Service/Repository 模板，也不建设微服务：

```text
workspace       项目、模块、Feature、仓库关系
specification   需求/架构/功能规格、修订、差异、基线
review          待审、评论、人工决定
execution       任务定义、授权、Run、事件
quality         用例、技术验证、证据、人工验收
change          Bug、未决事项、变更影响
release         发布范围、候选产物、交付
integration     MCP、上下文、导入导出
security        Owner、AI Client、Token
```

每个模块通常只保留：`routes.ts / service.ts / repository.ts / schemas.ts` 中真正需要的文件。HTTP Route 和 MCP Tool 只做协议适配；Service 负责业务规则；Repository 负责持久化。没有复用价值时不创建抽象基类、接口 + Impl 双层、通用 Factory 或事件总线。

## 3. 项目对象与粒度

### 3.1 主层级

```text
Project 项目
└── Module 模块
    └── Feature 功能增量
        └── Task 可授权工作单元
```

里程碑和 Release 是交付视图，引用 Feature，而不是创建另一份功能树。第一版不强制单独创建 Work Package；可以用里程碑分组满足阶段管理。后续确有跨模块工作包需求时再增加实体。

示例：

```text
PA 项目 A
├── MOD-01 项目基础
├── MOD-02 系统管理
│   ├── F-001 用户管理基础能力
│   ├── F-002 角色管理基础能力
│   └── F-003 菜单管理基础能力
└── MOD-03 设备接入
```

Feature 是一次可以完成验收的功能增量，不是永远重开的“用户管理总桶”。后续批量导入可新建 Feature，并关联原功能。

### 3.2 ID

| 对象 | 展示 ID | 说明 |
|---|---|---|
| Project | PA | 项目内命名空间 |
| Module | MOD-02 | 项目内唯一 |
| Feature | F-003 | 项目内唯一，不编码可变父级 |
| Task | F-003-T02 | 所属 Feature 内的工作单元 |
| 规格 | SPEC-013 / revision 7 | 内容对象和修订分离 |
| 基线 | BL-008 | 一组确定版本的批准依据 |
| Run | RUN-00128 | 一次实际执行 |
| 用例 | AC-M-05 | 稳定逻辑 ID，记录具体定义版本 |
| Issue | ISS-0009 | Bug、决策项或变更 |
| Release | REL-0.1.0 | 交付版本 |

数据库采用内部 ID，不依赖显示编号做关联。对外返回 ID 字符串，避免 JavaScript 大整数精度问题。保留旧编号 `P1-W01-E` 为别名，别名在项目内唯一；重名必须让用户选择，不能 AI 猜测。

### 3.3 Task 的合理粒度

按独立目标、风险、依赖和“这里是否需要暂停”划分。例如：

```text
设计与验收定义
→ 后端业务实现及测试
→ 前端交互及测试
→ 集成验证和必要修复
```

需要控制某个实现边界时再拆成独立任务。普通文件、类、DTO、数据访问层不自动成为任务；每个用例也不自动成为一个 Task。

任务必须有限：一个批准目标、一组输入、一组允许范围、一组可验证产出、一个停止点。新发现的附带优化只进入建议或变更草稿。

## 4. 需求和设计怎样保存

### 4.1 内容对象，不是文件夹

平台提供版本化规格对象 `Spec`。每个规格有类型、所属项目/模块/Feature、正文、稳定章节 ID、修订历史和引用。

项目级规格建议合并为三类，不强制生成三份文档：

| 类型 | 内容 |
|---|---|
| 项目需求与范围 | 使用者、目标、场景、包含/不包含、约束、成功条件 |
| 架构与技术选择 | 系统边界、组件职责、技术决策、数据流、部署、风险 |
| 交付与验证策略 | 首版范围、里程碑、验证方式、验收与发布要求 |

模块级只有存在共享规则时才需要独立规格。普通 Feature 默认一个规格，章节如下：

```text
scope             范围、非范围
requirements      功能规则及需求 ID
interaction       页面/交互/状态
implementation    必要的实现约束与代码入口
contracts         API/数据/资源引用
failure-recovery  异常、并发、恢复
dependencies      已确认和未确认依赖
acceptance        可执行验收条件
open-decisions    未决事项
```

章节可以因项目类型裁剪。没有数据库的游戏不出现空的数据库设计；存在存档时使用存档格式和兼容性设计。

### 4.2 内容格式

正文保留 Markdown，界面按稳定章节折叠和定位；章节目录可以由受控标记解析。初版不实现复杂块数据库、任意嵌套编辑器或在线协同算法。

结构化保存的不是全部句子，而是：身份、版本、关系、Task、Case、Issue、Review 和状态。叙述性规则保留 Markdown。二者通过稳定 ID 连接。

### 4.3 需求追踪，避免为了填表而填表

每条重要需求使用如 `REQ-U-03` 的 ID；每个验收项引用其覆盖需求。任务引用涉及的需求或功能条目。实际变更和测试证据再引用任务/用例。

```text
REQ-U-03 禁用用户后不能继续使用受保护功能
      ↓
Feature F-001 / Spec revision 7
      ↓
Task F-001-T02
      ↓
Run + 代码结果
      ↓
AC-U-03 + CheckRun
      ↓
人工验收 + Release
```

不强制每一行代码映射一个需求。代码位置关联用于导航和影响分析；“文件关联存在”不证明需求已经实现。

### 4.4 修订、评审与批准

每次有效保存产生一个不可变修订；保存时带 `expectedHeadRevisionId`。内容相同可返回 no-op，不产生无意义版本。两个客户端基于旧版本保存时，后者获得冲突响应，必须先读取差异。

评审比较“上一个批准版本”和“这次候选版本”，显示：变化章节、完整 Diff、关联任务/用例、未决项和建议影响。AI 摘要只是导航，原始 Diff 始终可展开。

批准针对不可变 Baseline，其中固定相关项目架构、模块规则、Feature 设计、验收定义版本。任务授权另固定任务定义快照和代码基线。

新草稿不自动撤销旧批准。新版本获批时由系统计算已知引用影响，并让人确认需要暂停/重新验证的范围；无法确定的影响标记待确认，不能悄悄沿用旧授权。

“当前已批准版本”和“最新草稿”同时显示。人工批准不能被一个 AI 上传的 `approved=true` 字段代替。

## 5. 页面与交互设计

### 5.1 六个一级入口

| 页面 | 默认内容 | 关键动作 |
|---|---|---|
| 项目总览 | 项目树、实施/验收/交付三类进度、阻塞、待我处理 | 创建/切换项目，进入功能 |
| 项目/Feature 工作台 | 概览、设计、任务、变更、测试、验收、历史 | 按需展开详细资料 |
| 评审中心 | 待设计批准、待任务确认、待决问题、待业务验收 | 看差异、批准、退回 |
| 执行记录 | 当前 Run、最后上报时间、阶段事件、文件和验证 | 查看真实记录，报告中断 |
| 版本与交付 | 发布范围、候选版本、证据、交付结果 | 验收和交付确认 |
| AI 接入与设置 | MCP 地址、Token、项目范围、配置片段、导入导出 | 接入 CLI，不管理模型账号 |

“需求新建”属于项目/Feature 工作台，不另外做一套聊天收件箱。输入简述保存为需求草稿，再复制带项目 ID 的规划指令给外部 AI。

### 5.2 项目树

树节点显示名称、生命周期、必要计数。点击 Module 展示共享设计和 Feature 汇总；点击 Feature 展示其工作台。

树按需加载；列表分页；不要一次向浏览器返回所有规格正文和历史 Run。搜索优先精确 ID、别名、标题和标签，随后检索正文。中文检索可先用有限范围全文/包含查询，再依据实际规模评估索引。

### 5.3 Feature 默认概览

```text
菜单管理基础能力  F-003（旧编号 P1-W01-E）
设计：待评审     实施：未核验     测试：未执行
当前可执行任务：无

本功能做什么：维护导航配置和已注册页面入口
不做什么：外链、任意组件路径、API 权限授予

待你决定：保护入口清单
待核实依赖：认证快照、首个路由消费者、已有库升级
本次变化：只读最新修订相对上次评审的差异

[功能设计] [任务] [代码结果] [测试] [人工验收] [历史]
```

此处“未核验”表示尚未检查真实仓库。导入的说明声称未实施，可以作为来源备注，但不能靠文档自动确认实际代码状态。

### 5.4 评审交互

设计评审：先显示变化和待决项，提供展开原文、逐章节评论、要求修改和批准基线。

实施评审：展示批准目标、实际改动、范围检查、测试来源、未执行项、未解决问题。用户可以“确认本次结果并授权下一项”，后台仍分别生成确认记录和新授权。

人工验收：按用例或验收组操作；显示候选构建和条件。通过/失败/不适用必须有相应结论。严重缺证据不能一键全部通过。

### 5.5 运行中进度的真实含义

平台能直接观察到 MCP 调用和证据上传；本地 CLI 的读文件、思考和 Shell 行为只有主动上报或采集器接入后才可显示。初版阶段事件是 `读取上下文 / 开始实施 / 开始验证 / 结果已提交`，不伪造逐文件实时轨迹。

页面始终区分“平台接收到”“客户端报告”和“独立验证”。没有新上报时显示最后联系时间和“当前情况未知”，不能自称 AI 正在执行某条命令。Token 用量不可获取时显示未提供，不估算为精确数。

## 6. 生命周期、任务和执行状态

### 6.1 Feature 生命周期

| 状态 | 含义 | 转换条件 |
|---|---|---|
| DRAFT | 范围草稿/待设计 | 创建对象 |
| DESIGNING | 正在设计 | 发生设计工作，尚无批准基线 |
| DESIGN_REVIEW | 待评审 | 候选规格已提交评审 |
| READY | 设计已批准、待实施 | 人批准必要基线 |
| IMPLEMENTING | 已有实施任务启动 | 有有效授权的 Run 开始 |
| VERIFYING | 整体技术验证中 | 必要实施任务已确认 |
| ACCEPTANCE_PENDING | 待人工业务验收 | 必要技术验证满足策略，无阻断问题 |
| ACCEPTED | 业务已验收 | 人确认绑定候选版本的验收 |
| DELIVERED | 已交付 | 交付范围和产物满足已批准条件 |

生命周期是服务端规则维护的投影；不提供 AI 任意设置该字段的接口。阻塞是附加信息，不把 IMPLEMENTING 覆盖成无法恢复原阶段的单一 BLOCKED。

### 6.2 Task 状态

`PLANNED → AUTHORIZED → RUNNING → SUBMITTED → CONFIRMED`

`SUBMITTED` 可以包含成功、失败或部分结果，不代表完成。人要求修改后，任务返回 PLANNED，补充新授权和新 Run；旧 Run 不覆盖。CANCELLED 是明确取消的终止状态。

设计任务不要求已经有设计批准，但权限只允许生成草稿。代码任务必须有批准基线和当前授权。小项目可以一次批准一个窄的“后端实现与测试”任务，不要求每个方法都审批。

### 6.3 Run 与结果

Run 状态：`RUNNING / SUBMITTED / INTERRUPTED / CANCELLED`。

Run 结果：`SUCCESS / FAILED / PARTIAL / BLOCKED`。执行过程中结果为空。失去联系只标记 stale，不等于 FAILED；人或客户端通过明确恢复/终止操作处理。

一个 Task 同时最多一个有效 Run。启动和提交使用幂等键及事务校验；第二个客户端不能同时领取。首版可限制同一项目只运行一个写代码 Run，使冲突管理保持简单。

### 6.4 四类人类决定

1. 批准设计基线。
2. 批准当前执行范围。
3. 确认任务成果。
4. 人工业务验收/交付确认。

界面可合并操作，但记录不能混淆。AI 凭证不具备这些权限；即使直接调用人类 REST 端点也必须被拒绝。

## 7. 授权与上下文

### 7.1 Task 定义

必填：目标、任务类型、所属范围、输入引用、依赖、产出、停止条件。

代码任务另外必填：仓库、允许/禁止修改范围、测试要求、需要覆盖的验收条目、基线约束。允许范围既包含业务范围，也包含路径范围。

示例：

```yaml
id: F-001-T02
kind: IMPLEMENTATION
objective: 实现用户启停业务规则及对应测试
baseline_id: BL-008
allowed_behavior:
  - 实现已批准的用户启停与会话失效规则
allowed_paths:
  - src/modules/user/**
  - test/user/**
forbidden_paths:
  - src/modules/auth/**
  - migrations/**
forbidden_behavior:
  - 新增角色权限体系
  - 修改公共身份协议
verification_profiles: [app-build, user-module-tests]
acceptance_refs: [AC-U-03]
stop_after: SUBMIT_RESULT
```

以上是平台记录/导出示意，不要求用户手写 YAML。

### 7.2 授权记录

授权固定：Task 定义版本、Baseline、允许范围、禁止范围、仓库、有效期、是否允许提交/推送/合并/部署、授权人和时间。

授权执行范围不得超出已批准设计与任务定义。需要扩大时重新提议，由人确认。默认不允许 push、merge、deploy；commit 可单独授权。

完成提交、撤销、期限到达或基线冲突均不能继续领取后续任务。MCP 写回不可用时先保存本地结果；不继续下一任务。

### 7.3 上下文分层

| 层 | 内容 | 加载方式 |
|---|---|---|
| 项目概要 | 范围、架构摘要、当前阶段、规范入口 | 小型摘要 |
| 当前目标 | Feature/Task、有效授权、待决项 | 一次定位 |
| 精确依据 | 批准规格章节、契约引用、依赖 | 按任务组装 |
| 代码范围 | 仓库 ID、相对路径、符号/测试入口 | 本地 AI 按需读 |
| 最近事实 | 上次 Run、未解决问题、证据有效性 | 摘要和按需展开 |

上下文返回必须包含 `baselineId / taskDefinitionVersion / authorizationId / requiredReferences / omittedReferences`。必要依据缺失时不返回 ready=true。不能为了减少 token 静默截断安全规则或验收条件。

读取代码范围可以按必要性扩展；修改范围不能自主扩大。项目文档和导入内容作为数据，不得覆盖平台授权规则。

## 8. Source of Truth 与导出

| 事实 | 权威位置 | 派生副本 |
|---|---|---|
| 原生需求、设计、模块、任务定义 | 平台数据库中的规格/对象版本 | Markdown/JSON 导出 |
| 当前状态、审批、授权、Run | 平台数据库 | UI、上下文快照、历史报告 |
| 代码与代码历史 | 对应 Git 仓库 | 上传的审查片段/补丁 |
| 可执行 API 契约和数据库 migration | Git 中指定文件 | 平台显示引用及版本 |
| 真实部署环境/迁移执行结果 | 该环境/部署记录 | 平台证据和关联 |
| 用例定义 | 对应批准规格修订的结构化用例快照 | 展示表格 |
| 测试和验收结论 | CheckRun/Acceptance 记录 | 进度和报告 |
| 原始证据 | 受管文件存储 | 数据库中的摘要、哈希和索引 |

平台里的 API 说明不能与 Git 中的 OpenAPI 同时独立维护同一契约字段。项目可暂时把契约作为规格草稿；正式采用契约文件后登记其 authoritative source，不允许两边互相覆盖。

批准后可生成便携快照：

```text
exports/PA/BL-008/
├── project.json
├── manifest.json
├── specifications.md
└── acceptance.json
```

可通过本地 AI 按已批准目录保存到仓库，再由有权限的一方提交。平台不因“导出”自动拥有 Git commit/push 权限。快照导出失败不伪造成功；基线保持批准事实，导出状态另记 PENDING/FAILED/EXPORTED。

导出不是完整备份。数据库、证据目录和必要运行配置均需备份；Token 不以明文导出，恢复后建议重新签发。恢复演练验证设计历史、批准记录和证据仍可关联。

## 9. 数据模型与约束

### 9.1 逐阶段创建，而不是首轮建齐所有表

以下是目标逻辑模型，实体随功能阶段落库。字段为开发设计依据，不是本轮生成可执行 SQL。业务项目自己的库表设计属于被管理规格，不应混入控制台数据库。

| 表/实体 | 主要字段 | 关键约束 |
|---|---|---|
| rd_project | id, project_key, name, project_type, scope_summary, version, archived_at | key 唯一；归档不删历史 |
| rd_unit | id, project_id, type(MODULE/FEATURE), parent_id, code, aliases, title, lifecycle, weight, version | 同项目父子；只有固定两层；禁止环 |
| rd_repository | id, project_id, repo_key, remote_url, kind | 不以服务器绝对路径作为唯一身份 |
| rd_spec | id, project_id, owner_type, owner_id, kind, head_revision_id, approved_revision_id | head 和 approved 分离 |
| rd_spec_revision | id, spec_id, revision_no, base_revision_id, markdown, sections, content_hash, author_id, created_at | 正文不可覆盖；spec+revision 唯一 |
| rd_baseline | id, project_id, scope_ref, references_json, content_hash, created_by, created_at | references 固定精确版本；同项目校验 |
| rd_review | id, target_type, target_id, candidate_hash, status, decision, actor_id, comment, created_at | 人类决定从服务端身份获取；决定不可覆盖 |
| rd_task | id, project_id, feature_id或项目作用域, code, kind, definition_json, definition_version, state, weight, version | 授权后定义冻结；草稿修改需乐观锁 |
| rd_grant | id, task_id, baseline_id, task_snapshot, effective_scope, repo_id, capabilities, expires_at, revoked_at, actor_id | 仅人签发；任务/项目/基线一致 |
| rd_run | id, task_id, grant_id, client_id, state, outcome, repo_snapshot, result_json, started_at, submitted_at, idempotency_key | 每任务最多一个有效 Run；提交幂等 |
| rd_event | id, project_id, target_ref, run_id, kind, actor_id, client_seq, payload, created_at | 追加事件；同 Run 序号去重 |
| rd_case | id, project_id, case_key, spec_revision_id, requirement_refs, type, steps, expected, required | case_key+spec_revision 唯一；批准后定义不可改 |
| rd_check_run | id, run_id, candidate_ref, case_snapshot, profile_snapshot, environment, status, provenance, results, evidence_refs | 同候选、同用例版本才能汇总 |
| rd_evidence | id, project_id, run_id, storage_key, filename, mime, size, hash, provenance, state | 只能绑定同项目；服务端校验大小和哈希 |
| rd_acceptance | id, target_ref, baseline_id, candidate_ref, case_results, conclusion, actor_id, created_at | 仅人确认；历史不可覆盖 |
| rd_issue | id, project_id, feature_id, type, severity, status, source_ref, affected_refs, description, resolution_ref, version | AI 可提问题/建议；不能擅自关闭阻断问题 |
| rd_release | id, project_id, version_name, scope_snapshot, candidate_refs, acceptance_refs, delivery_status, decision_ref | 发布范围固定；交付由人批准 |
| rd_link | id, project_id, source_ref, relation, target_ref | 关系类型白名单；同项目及目标存在检查 |
| rd_actor | id, type(OWNER/AI_CLIENT/后续COLLECTOR), display_name, login_name, password_hash(仅Owner), disabled_at | 初版单 Owner；AI 不可升级为 Owner；密码只存安全摘要 |
| rd_token | id, actor_id, token_hash, prefix, scopes, project_scope, expires_at, revoked_at | 只存摘要；仅首次显示明文 |

核心关系使用明确外键或等效事务校验；`rd_link` 只用于需求/代码导航和影响关系，不替代全部结构化关联。

任务定义、基线引用等小型快照可用 JSON；经常筛选的状态、归属和时间必须是明确列。禁止把全库做成无约束 EAV/万能 JSON 表。

### 9.2 并发与事务

- 草稿保存、任务定义修改携带 expectedVersion；冲突返回 409 和当前版本，不静默覆盖。
- 批准操作检查候选版本是否仍是人看到的版本；防止浏览器旧页面批准新内容。
- 启动 Run 在事务内检查授权、状态、依赖并占用任务；多客户端竞争只能一方成功。
- 提交结果和状态转换在同一数据库事务中完成；证据先上传完成再引用，缺失附件不能伪造已收齐。
- Idempotency-Key 绑定调用者、端点/工具、请求体摘要；同键同内容返回原结果，同键异内容返回冲突。
- 授权撤销后仍可接收正在执行任务的最终说明和已有证据，但标记 revoked_context，不允许按正常完成推进。
- 不能仅使用内存锁维护关键互斥，否则重启后容易破坏规则。首版单实例也用数据库条件更新/事务保证。

### 9.3 删除和审计

业务对象优先归档。已批准修订、审批、Run、验收和交付记录不提供 AI 删除接口。普通草稿可由人取消；清理过期原始日志遵循保留策略，保留结果摘要和删除记录，不制造可点击但不存在的证据链接。

## 10. 代码关联、Diff 和仓库边界

平台保存仓库 ID、代码基线、结果 Commit 或补丁摘要、路径和必要片段。代码正文仍属于 Git。

本地 Windows 路径只保存在本机绑定配置；服务端在 Linux 上也不能直接打开 `D:\Projects\demo`。没有远程 Git 集成时，由本地 AI/采集器上传审查包，或者在浏览器手工上传。

Diff 必须相对本次 Run 开始时确认的基线，覆盖：已经提交的变化、暂存/未暂存变化、新文件、删除、重命名、二进制资源和文件模式变化。只运行一次普通 `git diff` 可能漏掉已提交/已暂存/未跟踪内容，不能把空输出当成没有变更。[S09]

检测到已有用户未提交修改时，不默认清理。首次版本建议要求清晰的干净基线，或由人明确接受带有原始差异摘要的工作区。无法区分来源时停止，而不是把所有本地变化都归给 AI。

每个 Run 不强制创建 worktree。单人串行可使用一个 Feature 分支；并行或需要隔离工作文件时再使用 worktree。Git worktree 共享仓库相关元数据，不是操作系统安全沙箱；删除它之前必须保存并核对未提交结果。[S09]

## 11. 测试与验收

### 11.1 分层结果

```text
实施产物提交
→ 任务成果确认
→ Feature 技术验证
→ 人工业务验收
→ 指定版本交付
```

Task 自身必须运行其要求的测试；后续 Feature 技术验证检查多部分集成。并不是先写完全部代码才考虑测试。

每个 CheckRun 保存：命令或测试配置快照、工作目录标识、代码/构建版本、环境、用例版本、开始结束时间、退出码、通过/失败/跳过数、证据来源、原始报告引用。

### 11.2 状态与证据来源分别保存

测试状态：NOT_RUN / RUNNING / PASS / FAIL / BLOCKED / SKIPPED。

来源：

| provenance | 含义 |
|---|---|
| AI_REPORTED | 外部 AI 上报；即使附报告也不能冒充独立执行器 |
| COLLECTOR_RECORDED | 本地辅助工具记录命令、退出码和文件摘要 |
| CI_VERIFIED | 经登记的独立 CI 结果和签名/可信回调核实 |
| HUMAN_REVIEWED | 人审查并确认相应材料；不是把手测伪装成自动测试 |

采集器与 AI 在同一账号、同一可写机器上时不构成防恶意伪造的强信任边界。来源分层用于说明证据形成方式，不宣称绝对真实性。

默认技术门禁要求关键验证通过且存在报告、版本一致、未覆盖项明确。仅 AI_REPORTED 的关键结果进入“待证据确认”，人确认或独立验证后再推进。可以按项目配置允许的证据策略，但必须清楚展示策略，不把弱证据隐藏。

SKIPPED 和 N/A 不等于 PASS。确需豁免，由人记录理由、影响和期限；不能把测试计数全部改为通过。

### 11.3 三个验收视角

Feature 验收：这次功能增量是否满足规则。

Module 验收：多个 Feature 之间的共享权限、数据、交互是否一致。

Release/工作包验收：本次承诺的整体业务链和交付目标是否成立。

一次演示可复用证据覆盖多个视角，不强制重复开会或重复写报告。

### 11.4 候选版本变化

通过结果只适用于所记录的规格和代码/构建。修改代码、合并冲突、改变依赖或重新构建后，先判断受影响验证，再重跑必要项。证据仍留在历史，但当前视图标记 STALE，不静默继承。

人工验收绑定确定的候选 Commit/构建/资源包。无 Commit 的早期审查可以使用不可变补丁摘要，但最终交付应有可识别和可复现的版本。

## 12. 问题、返工与持续扩展

Issue 分三类即可：BUG、DECISION、CHANGE。不要每条聊天意见都创建独立工单。

Bug：关联发现时的 Run、需求/用例和候选版本；修复有明确 Task，补充回归用例，原问题记录不覆盖。

Decision：用于会阻止设计、实施或验收的未决项；必须写清阻塞哪个范围。菜单保护清单可能只阻塞保护路径验收，不应无理由阻塞所有菜单树读取开发。

Change：已批准范围或设计调整。先生成新草稿，列出影响，再批准相关基线和任务。不要靠修改测试期望把已批准规则改掉。

可以在同一个已授权任务内修复自身引入的问题并重跑测试，只要没有改变批准目标、范围和契约。超出范围或涉及公共设计时停止并提出变更。

## 13. 进度计算

项目默认显示三类进度：工程实施、人工验收、交付。设计用“批准/待评审/未完成/待核实”显示，必要时展示必需章节完成数，不显示 AI 凭空填写的 90%。

Feature 内实施进度：已确认实施 Task 权重 / 已承诺实施 Task 总权重。权重用简单的 1/2/3/5，批准计划时固定。

项目实施进度：按 Feature 范围权重加权汇总。人工验收进度按已 ACCEPTED 的 Feature 权重计算；交付按 DELIVERED 计算。Module 和 Release 视图引用同一 Feature，不重复计数。

新增范围必须记录分母变化。未展开的远期功能显示“未估算”；没有足够基线时展示数量和状态，而非虚构百分比。零任务、全部不适用等情况返回 N/A，不能除零或默认 100%。

自动验证同时展示覆盖率和运行结果，例如“必需场景已覆盖 8/10；本次测试 24/24 通过”，不能用测试文件条数代表需求覆盖。

## 14. 旧 Markdown 迁移

推荐逐个活动 Feature 迁移，不一次清洗整个文档库：

```text
读取已有文件/粘贴正文
→ 保留原文、文件路径与哈希
→ AI 提取范围/能力/用例/依赖/未决项草稿
→ 人查看导入差异
→ 选择转为平台原生规格
→ 原文件改为来源归档或只读导出
```

初版不自动执行 Markdown 中的指令，不访问任意链接，不扫描全磁盘。导入的链接仅作为待解析引用。

来源模式明确区分：

- ARCHIVED_SOURCE：原文备查，不参与当前状态判断。
- EXTERNAL_REFERENCE：尚未迁移，平台只展示其引用/版本；修改权仍在原位置。
- NATIVE_SPEC：经确认迁入，后续在平台生成修订；原文件不再双向编辑。

你提供的菜单管理材料可以提取 M-01～M-08、验收场景和依赖。它说明本轮只做设计、业务验收未执行；因此导入初始状态为待评审和验收未执行。真实代码状态仍需一次仓库核验，未读取的 B/C/D 关联资料标记待核实，不能自动认证其已完成。

## 15. 通用项目模板

模板只是章节、检查项和建议任务类型，不是代码生成器，更不是可执行插件市场。首版使用固定、可版本化的模板定义；后续允许编辑模板，但不允许运行模板里的任意脚本。

| 内容 | Web 项目 | Godot 游戏 | 通用工具 |
|---|---|---|---|
| 需求 | 用户与业务流程 | 玩家目标与核心循环 | 使用场景与输入输出 |
| 架构 | 前后端、模块、数据 | 场景/节点/脚本/资源职责 | 程序模块与集成 |
| 数据设计 | 数据库/缓存/契约 | 配置、资源、存档版本 | 文件格式或本地数据 |
| 实施 | Backend/Frontend 等 | Gameplay/UI/Asset 等 | Core/UI/Integration |
| 自动验证 | 单元/接口/集成 | 脚本、数据、存档与可自动化场景 | 单元/兼容/集成 |
| 人工验收 | 业务操作 | 试玩、手感、视觉/音效 | 实际工作流程 |
| 交付 | 构建包与部署 | 导出包与目标平台 | 安装包/脚本/可执行文件 |

Godot 官方支持命令行运行和导出等能力，但引擎启动成功不代表游戏玩法和画面通过验收；自动验证配置必须针对具体项目，手感和视觉保留人工验收。[S10]

## 16. 安全与非功能要求

### 16.1 最小认证

Owner 通过本地安装初始化；首次创建不能开放给任意公网访问者。网页会话使用安全 Cookie/CSRF 防护。AI 使用独立 Token，按项目限制读取、草稿写入和执行写回权限。

`project:draft:create` 是单独能力，允许用户授权的规划客户端创建新项目草稿；它不赋予批准、删除、部署或修改所有其他项目的权限。

MCP 官方 SDK 只提供协议与传输能力，平台仍必须自己实现业务认证、项目作用域和工具权限。MCP 端点启用 Token 校验、Host/Origin 防护、请求限额和工具级权限，不因为“在本机”就裸露写接口。Streamable HTTP 的安全要求以当前 MCP 协议为准。[S05][S11]

### 16.2 不暴露的能力

认证后的请求主体由服务端显式传入 Domain Service；异步调用时也必须正确传递并隔离主体，不能依赖可被并发请求串用的全局可变变量，更不能接受工具参数伪造主体。

没有通用 `execute_sql`、`shell_exec`、`read_any_file`、`set_status`、`grant_self` 工具。MCP 工具参数不能注入审批人、任意服务器路径或外部回调地址。

上传限制大小、数量和 MIME；存储键由服务端生成；拒绝路径穿越。日志、Diff、报告进行秘密检查与脱敏，禁止默认上传 `.env`、私钥、完整用户数据和凭证。

Markdown 渲染禁用或清理危险 HTML；外链明确提示；代码和文档内容不作为高权限指令。

### 16.3 本地外部 AI 的硬边界

平台可以强制执行自己的 API 权限、版本和状态规则。外部 CLI 拥有操作系统文件权限时，仍可能在不调用平台的情况下修改本地代码。AGENTS.md、CLAUDE.md、MCP 授权和路径检查不能形成绝对阻断。[S02][S03]

需要更强隔离时，后续使用独立工作目录、受限工具/系统账号、沙箱和受保护合并/部署流程。本项目 v1.1 只承诺“流程可控、越界可检查、结果有来源”，不承诺不可绕过的本地安全执行环境。

### 16.4 建议验收负载，不是实测性能

建立种子数据：10 个项目、每项目 30 个模块/300 个 Feature、总计 10,000 个任务与执行记录。在选定部署机上测分页、树加载、详情和上下文接口，记录 CPU/内存/数据库规模。

建议页面首屏和普通上下文请求目标为秒级；具体阈值在 S0 以机器与数据量确认。不得把这个目标写成已达成的资源/性能结论。

### 16.5 可靠性

备份要覆盖数据库和证据目录；做一次恢复验收。导出和大报告处理可以使用单体内受限后台任务，但不要因此引入独立队列集群。重启后待完成任务从数据库恢复状态，不能只靠内存集合。

## 18. 从新需求到交付的完整例子

### 18.1 新 Web 系统

人描述设备台账系统目标 → 外部 AI 创建项目草稿 → 写需求/架构候选/模块树/首版 Feature/阶段计划 → 提出待决项 → 人批准首版范围和关键架构。

远期模块只给边界和依赖，当前迭代的用户管理才细化接口、数据、业务规则、任务和验收。避免一次为 50 个模块生成无人能评审的细节。

用户管理设计获批 → 人批准后端任务 → AI 获取上下文、核对本地仓库并启动 Run → 编码、测试、写回报告和 Diff → 人确认 → 批准前端 → 集成验证 → 人业务验收 → 交付。

### 18.2 Godot 游戏

人描述“2D 采集经营原型” → AI 创建 GAME_GODOT 项目 → 规划核心循环、输入、场景、资源/存档、模块与首次可玩版本 → 人批准范围。

`背包基础` Feature：规则包括堆叠上限、满包反馈和存档恢复；任务可以是数据模型、交互界面、自动验证和试玩。代码范围是 GDScript/场景/资源目录，不生成 Web 后端专属层。

AI 通过同样的 MCP 接口读写；本地用 Godot 工具执行项目约定检查，截图/录屏和导出包作为证据。试玩手感由人验收，自动测试不能替代。

### 18.3 已交付后继续扩展

已有背包基础已交付 → 新建 `背包排序与分类` 增量 → 引用原有设计和存档约束 → 产生新批准基线和任务 → 回归原有行为 → 发布新版本。

旧版本的批准、Run、验收和交付历史始终可查，不用把旧 Feature 的“已完成”抹掉来容纳所有未来变化。

## 19. 开工判断

满足以下条件才进入 S1：确认系统边界、事实来源、候选技术栈、第一阶段真实 MCP 目标和不变量；其余详细实现按阶段评审。

本方案不要求先开发所有数据表、所有流程和所有页面。开发顺序和每阶段停止点见 [02-分阶段开发与验收计划](02-分阶段开发与验收计划.md)。协议和官方技术依据见 [03-外部AI接入与执行协议](03-外部AI接入与执行协议.md)。

# AI 研发控制台：分阶段开发与验收计划

版本：v1.1 · 日期：2026-09-18 · 状态：待评审，所有实施项未执行

## 1. 开发方式

采用“一个可运行闭环逐步扩展”的顺序，不先建立全部表、页面和接口空壳。

**第一阶段就验证本地 Codex 和 Claude Code 能真实读写控制台。**MCP 不是最后追加的插件，也不是只写配置但没有真实数据操作的演示。

每个任务包含：目标、允许范围、输入依据、需要验证的结果和停止点。任务完成后提交结果，等待人工确认下一任务。一个已批准任务内部可以修复自身缺陷，但不能借机增加后续阶段功能。

阶段不是时间承诺。未了解实际开发时间和已有代码前，不给“几天全部完成”的保证。

## 2. 阶段总览

| 阶段 | 版本目标 | 核心交付 | 可用效果 |
|---|---|---|---|
| S0 | 方案冻结 | 范围、候选依赖、数据与协议审查、首批任务 | 人知道第一步具体做什么 |
| S1 | v0.1：AI 读写项目 | 基础登录、AI Token、项目与规格草稿、真实 MCP | 在 Codex/Claude 创建项目、写设计，网页立即可查 |
| S2 | v0.2：设计和评审 | 模块/Feature、版本 Diff、基线、任务草稿、上下文 | 不用翻几十个 MD 评审方案 |
| S3 | v0.3：受控实施 | 人工授权、Run、事件、结果/报告/补丁写回 | 外部 AI 领取当前任务，在本地实施测试并提交 |
| S4 | v0.5：验证与交付 | 用例、证据核对、技术门禁、人工验收、交付 | 实施、测试、业务验收和交付不再混淆 |
| S5 | v1.0：可持续使用 | 旧文档迁移、Web/Godot 模板、导出/恢复、跨项目验证 | 能长期管理真实项目，并逐步扩展 |

可选的本地采集器、CI 连接、多 AI 并行、Git 平台深度集成放到 v1.0 之后，不阻塞最早的读写和实施闭环。

## 3. S0：确认蓝图与技术基线

### S0-T01 范围和界面核对

输入：`01` 和 `03`。

产出：确认产品边界、六类页面、主对象层级、事实来源和外部 AI 执行边界；列出真正阻塞开工的问题。已有信息足够的内容不得重复询问。

不得做：业务代码、完整 UI、自动构建二十张表、引入模型服务。

验收：负责人能说明“平台在哪里、AI 在哪里运行、代码在哪里、测试由谁执行、谁有批准权限”。

### S0-T02 协议和兼容性检查

核对官方依赖系列和实际本地工具版本，固定 Node.js LTS、Fastify、MCP TypeScript SDK、SQLite/Drizzle、Vue/Vite 依赖组合；设计最小 MCP 联调步骤。此任务可以读取环境和官方文档，但编写技术验证代码需要单独明确允许。

产出：一页技术基线记录、S1 第一个闭环的输入/输出、发现的兼容性风险。

验收：不把“文档声称兼容”写成“项目已实测”；客户端配置中的地址和 Token 来源明确。

### S0-T03 审核首批任务

只细化 S1。后续阶段保留本文件粒度，不提前生成全部实现类清单。

产出：批准或要求修改的 S1 任务，以及可用端口、数据库、Owner 初始化方式。

**退出条件：S1 范围获批。没有批准时停止。**

## 4. S1：真实 MCP 项目读写

### 4.1 产品切片

用户首次打开网页，初始化 Owner，创建一个 AI Client Token。Codex 和 Claude Code 分别配置该 Token 后，能创建草稿项目、保存规格、按 ID 读取内容；网页显示同一份数据。

不要求 S1 已经支持任务实施。所有设计明确显示草稿，不能变相授权代码。

### 4.2 任务

| Task | 目标 | 范围 | 必须验证 |
|---|---|---|---|
| S1-T01 | 最小应用与认证边界 | Fastify + Vue 最小壳、SQLite迁移、Owner会话、AI Token | 匿名拒绝、Token撤销、两类身份分离 |
| S1-T02 | 项目与规格保存 | Project、Spec、不可变Revision、基础页面、REST | 保存后读取一致；重启持久化；旧版本冲突 |
| S1-T03 | MCP 接入 | 仅已完成的读写工具、官方 MCP TypeScript SDK/Fastify 适配、配置说明 | Codex/Claude真实连接和写回，无模型API依赖 |

S1-T01 页面只需完成初始化/登录和连接设置的必要部分，不建设通用 RBAC。Token 项目作用域和创建草稿能力必须有明确限制。

### 4.3 最小数据与接口

数据：`rd_actor / rd_token / rd_project / rd_spec / rd_spec_revision / rd_event`。仅创建当前需要的列、索引和迁移。

REST：登录、退出、会话、Token 签发/撤销、项目查询/创建、规格读取/保存。

MCP：`rd_project_list / rd_project_create / rd_outline_read / rd_spec_read / rd_spec_save`。

AI 不得通过端点设置 approved、lifecycle、actorType 或 Owner 身份。创建操作使用幂等键；规格更新使用预期版本。

### 4.4 可演示流程

```text
人创建 AI Token
→ Codex 创建 DEMO-WEB 项目
→ 写“项目目标与需求”草稿
→ 网页看到原文和 revision 1
→ Claude Code 读取相同规格
→ 基于 revision 1 提交 revision 2
→ 网页查看两个版本
```

### 4.5 验收

| 编号 | 操作 | 预期 |
|---|---|---|
| S1-AC01 | 无 Token 调 MCP | 拒绝；无数据库写入 |
| S1-AC02 | AI Token 调 Owner 管理接口 | 拒绝，不能签发权限或变更自身身份 |
| S1-AC03 | 允许新建草稿的 AI 创建项目 | 草稿创建，默认不存在设计批准和实施授权 |
| S1-AC04 | Codex 保存、Claude 读取 | 内容、项目、版本一致 |
| S1-AC05 | 重复发送创建请求 | 返回同一结果，不重复建项目 |
| S1-AC06 | 两个客户端基于同版本修改 | 后提交的旧版本修改冲突，不覆盖 |
| S1-AC07 | 服务重启后读取 | 数据保留 |
| S1-AC08 | 撤销 Token 后继续请求 | 拒绝；界面可见撤销记录 |
| S1-AC09 | Token只允许项目A，却读写项目B | 拒绝，不泄漏项目B正文 |
| S1-AC10 | 网页/MCP查看规格 | 同一数据，不存在两套存储 |

S1 不计入：Feature 完成度、AI 自动编码、浏览器远程运行命令、独立验证通过。

**退出条件：两个目标客户端都完成真实读写演示并保存证据。受环境限制未完成的客户端标记未验证，不宣称兼容通过。**

## 5. S2：项目树、设计差异与人工评审

### 5.1 产品切片

外部 AI 把需求转为模块/Feature/任务草稿和完整规格；负责人在页面查看本次变化、未决项和影响，然后批准设计基线。

### 5.2 任务

| Task | 目标 | 范围 | 必须验证 |
|---|---|---|---|
| S2-T01 | 模块与Feature工作台 | 固定层级、旧ID别名、概要、草稿计划批量写入 | 同项目约束、层级无环、批量幂等 |
| S2-T02 | 设计评审与版本Diff | 修订比较、评论、评审请求、批准基线 | 精确版本审批、草稿不覆盖批准内容 |
| S2-T03 | 任务草稿与上下文 | 任务定义、依赖、用例草稿、代码引用、上下文读取 | 缺依据必须报出；无授权不能返回可执行 |

批量写入只允许类型固定的草稿操作；首版每批最多 25 项，全部成功或全部失败，不允许“已保存一半但显示完成”。新增对象使用客户端临时键，服务端返回真实 ID 映射。

### 5.3 关键界面

项目树 → Feature 概览 → 设计折叠章节 → 修订 Diff → 待审中心。

首版 Diff 可以是简单文本差异，不要求一次实现复杂代码查看器。评审页必须比直接读原文更快，但完整原文始终能展开。

### 5.4 可用性限制

S2 可以批准设计和保存任务，但代码执行授权按钮暂不启用，直到 S3 的启动/提交/确认闭环就绪。否则会出现“能批准执行，却没有结果记录能力”的半成品流程。

API 返回明确 `CAPABILITY_NOT_READY`，不暴露尚未实现的 MCP 工具。设计草稿编辑仍正常可用。

### 5.5 验收

| 编号 | 操作 | 预期 |
|---|---|---|
| S2-AC01 | 保存几十个模块/Feature草稿 | 项目树正确，正文按需读取 |
| S2-AC02 | 批量项包含非法父级 | 整批拒绝或明确失败，不留不可解释半成品 |
| S2-AC03 | 以旧别名定位Feature | 返回唯一对象；冲突时要求选择 |
| S2-AC04 | 人查看revision 3时AI创建revision 4 | 不能把人对3的操作误认为批准4 |
| S2-AC05 | revision 3批准后创建4草稿 | 3仍可作为当前批准依据，4明显标记草稿 |
| S2-AC06 | AI自填approved=true | 拒绝或字段校验失败，不产生批准 |
| S2-AC07 | 缺失被引用的必要规格 | 上下文标记不完整，不允许执行 |
| S2-AC08 | 变更摘要遗漏一项规则修改 | 原始Diff可查，不只依赖AI摘要 |
| S2-AC09 | 依赖A指向B，B指向A | 检出环或阻止设为可执行计划 |
| S2-AC10 | 只有设计，没有实施记录 | 不显示“功能已完成” |

**退出条件：用户能只通过页面评审一个真实功能设计，并看见批准版本、下一任务和未决项。**

## 6. S3：外部 AI 实施与结果写回

### 6.1 产品切片

人批准一个窄任务；AI 读取当前授权，在本地业务仓库编码和测试，提交 Run、验证报告和必要补丁。平台不启动 CLI，不提供 Shell 接口。

### 6.2 任务

| Task | 目标 | 范围 | 必须验证 |
|---|---|---|---|
| S3-T01 | 授权和启动互斥 | Grant、Task状态、Run启动、撤销、期限 | 无授权拒绝、重复领取、旧基线 |
| S3-T02 | Run事件与提交 | 阶段事件、结果、问题、幂等写回、断线恢复 | 重复提交、提交失败、迟到结果 |
| S3-T03 | 审查包与证据上传 | 受限上传、变更清单、补丁/报告、来源标记 | 不信任任意本地路径、大小/MIME/哈希校验 |
| S3-T04 | 页面评审和下一步 | Run详情、人工确认、进度、复制执行指令 | 确认和下一授权分开，不自动继续 |

必要任务定义引用需支持仓库标识和相对路径。不能要求用户把全部源码同步给平台才能执行。

### 6.3 最早完整场景

创建独立样例仓库，只含一个很小的用户管理规则。批准唯一任务：实现禁用规则和对应测试，不允许新增前端和数据库。

Codex 完成该任务并提交；网页展示文件、结果来源和报告；人确认。随后 Claude Code 根据新会话读取最新事实，不能重复执行已经提交的任务，也不能自行开始前端。

### 6.4 验收

| 编号 | 操作 | 预期 |
|---|---|---|
| S3-AC01 | 未批准时调用run_start | 拒绝，不创建运行中的Run |
| S3-AC02 | 两个AI同时启动同一Task | 仅一个成功 |
| S3-AC03 | 同一幂等键重试启动 | 返回原Run |
| S3-AC04 | task_context取出后授权被撤销 | run_start重新检查并拒绝 |
| S3-AC05 | 只允许一个模块目录但提交到禁止目录 | 标记越界，不能自动确认 |
| S3-AC06 | AI提交成功Run | Task为SUBMITTED，Feature不是ACCEPTED |
| S3-AC07 | AI直接请求确认人工验收 | 拒绝 |
| S3-AC08 | 提交响应丢失后重试 | 不重复保存、不重复推进 |
| S3-AC09 | 服务离线 | AI保存本地结果、停止；页面不伪造实时进展 |
| S3-AC10 | Run执行中被撤销，随后报告到达 | 留存证据且标记撤销上下文，不能正常推进 |
| S3-AC11 | 已提交代码/暂存/新文件混合存在 | 审查包不只包含单一git diff输出 |
| S3-AC12 | 上传声称是本机D盘路径 | 服务端不尝试打开；要求实际上传或可验证引用 |

| S3-AC14 | 人确认T02 | 不自动授权T03；可显式合并按钮完成两项记录 |

**退出条件：两个客户端至少分别参与一个真实“读授权—本地改代码—测试—写回”闭环，证据来源正确显示。**

## 7. S4：技术验证、业务验收与交付

### 7.1 产品切片

把设计中的验收条件变成可定位的 Case；技术结果与人工结论分别记录。代码/构建变化后识别证据过期；按候选版本完成交付。

### 7.2 任务

| Task | 目标 | 范围 | 必须验证 |
|---|---|---|---|
| S4-T01 | 用例和验证 | Case版本、CheckRun、需求映射、结果表 | 用例/代码/环境匹配；未执行不算通过 |
| S4-T02 | 证据确认和Bug闭环 | 来源策略、报告审查、Issue、回归关联 | AI上报不冒充独立CI；修复需对应证据 |
| S4-T03 | 人工验收 | Feature/Module/Release作用域、通过/失败/不适用 | 仅Owner确认；绑定候选版本 |
| S4-T04 | 发布与进度 | Release范围、交付记录、三类进度、证据失效 | 不重复计算、不直接平均模块百分比 |

不自动部署生产系统。交付可以是“生成并交付安装包”或“确认目标环境已部署”，依赖项目模板和人的授权。

### 7.3 验收

**退出条件：一个真实功能完成技术验证、人工验收和交付记录；历史可以从需求追到候选产物。**

## 8. S5：旧资料迁移、通用模板和长期维护

| S5-T01 | Markdown导入 | 原文保存、结构提取、引用映射、人工确认 | 不从文档推断代码完成；不自动批准 |

| S5-T04 | 长期使用验收 | 多项目、检索、版本扩展、样例负载、完整文档 | 两类项目共用协议，无硬编码Web专属阶段 |

### 8.2 菜单管理导入演示

## 9. 后续扩展顺序

只在痛点出现后增加：

| 优先条件 | 扩展 | 不能改变的原则 |
|---|---|---|
| 手工收集报告和Diff成为瓶颈 | 本地轻量采集器 | 不直接等同强可信沙箱 |
| 需要独立验证 | CI接入、签名/回调核对 | 不能把AI自报来源升级为CI |
| 需要两项任务同时实现 | worktree与冲突范围检测 | 同Task唯一有效Run |

| 文档规模确实过大 | 检索索引/语义辅助 | 批准版本和任务引用仍是执行依据 |

第一版不预建这些全部框架或空适配器。

# AI 研发控制台：外部 AI 接入与执行协议

版本：v1.1 · 日期：2026-09-18 · 状态：拟定接口契约，尚未实现/联调

> 本文所有 `rd_*` 工具、`/api/v1/*` 业务端点和示例地址均属于待开发的控制台，不是 Codex/Claude 自带功能。本地客户端接入方法依据官方文档核查，具体平台服务仍需开发并验证。

## 1. 接入方式的确定

主路径：**Streamable HTTP MCP → 控制台业务 Service**。

人使用浏览器 REST；外部 AI 使用 MCP；大文件证据使用受限 HTTP 上传。三者共用项目、版本、权限和状态规则。

平台服务示例地址：`http://127.0.0.1:8787`；MCP 示例端点：`http://127.0.0.1:8787/mcp`。这是设计默认值，开工时确认端口是否冲突。

不采用：模拟 AI 点击网页、用浏览器自动化读页面、AI 直接操作控制台数据库、为每个 AI 写一套独立 REST 逻辑、订阅转 API、平台远程启动用户电脑终端。

### 1.1 为什么采用 Node 原生 MCP，而不再引入 Java/Spring 层

平台本身已经需要 Node/TypeScript 前端构建环境，而 MCP 官方 TypeScript SDK v2 直接提供服务端、Streamable HTTP 以及 Fastify 中间件。因此本项目不再为 MCP 单独引入 Spring Boot/Spring AI。[S04][S05]

推荐：同一个 Fastify 应用同时提供 `/api/v1/*`、`/mcp` 和前端静态资源。MCP Tool Handler 与 REST Route 只做协议适配，统一调用 Domain Service。

```text
REST Route ─┐
            ├─ Domain Service ─ Repository ─ SQLite
MCP Tool ───┘
```

不手写 MCP JSON-RPC，不引入模型供应商 SDK，不把 MCP Tool 写成第二套业务系统。只有官方 SDK 在目标客户端真实联调出现不可解决的兼容问题，才评审薄适配器。

### 1.2 本地与远程

首版推荐同机部署：Fastify 监听 `127.0.0.1`，默认端口示例 `8787`。`127.0.0.1` 指当前运行 CLI 的机器；若 Codex/Claude 在 WSL、容器或另一台机器中运行，必须确认实际网络可达性。

远程部署使用 HTTPS 和认证，不把 Bearer Token 发送到公共明文网络。网页 Owner Cookie 与 MCP Token 完全分离。

生产模式可以让 Fastify 直接托管构建后的 Vue 静态文件，因此不需要 Nginx 才能运行；只有 TLS、反代、统一域名等实际需求出现后再加入反向代理。

## 2. 快速接入：控制台完成 S1 后使用

### 2.1 平台准备

负责人在网页完成 Owner 初始化，为 Codex 和 Claude 分别签发 AI Token。Token权限至少包含已授权项目的读取、草稿写入；需要AI创建新项目时再开放“创建项目草稿”。

Token 不是 OpenAI/Anthropic API Key。平台不读取或保存外部 CLI 的模型账号与订阅凭证。

界面生成不含明文凭证的配置片段；实际 Token 放在本地环境变量或相应安全存储里。不要把 Token 写入 Git、截图、聊天或运行日志。

### 2.2 Codex

在用户的 Codex 配置中合并以下片段，不覆盖已有内容。官方支持 HTTP MCP 的 `url` 和 `bearer_token_env_var`。[S01]

```toml
[mcp_servers.rd-console]
url = "http://127.0.0.1:8787/mcp"
bearer_token_env_var = "RD_CONSOLE_CODEX_TOKEN"
```

Windows 用户配置通常位于 `%USERPROFILE%\.codex\config.toml`；存在自定义 Codex home 时按实际位置处理。环境变量需要对启动 Codex 的进程可见，不会自动注入已经运行的进程。

在准备好环境变量之后：

```powershell
codex mcp list
```

随后在目标项目仓库启动 Codex。检查配置存在不等于已经通过读写验收；必须实际调用控制台工具创建/读取测试对象。CLI 参数发生差异时先查看本地 `codex mcp --help`，不要猜一个不存在的参数。[S01]

### 2.3 Claude Code

推荐由控制台生成项目根目录 `.mcp.json` 的待合并片段。Claude Code 官方支持 HTTP server 和 headers 中的环境变量展开。[S12]

```json
{
  "mcpServers": {
    "rd-console": {
      "type": "http",
      "url": "http://127.0.0.1:8787/mcp",
      "headers": {
        "Authorization": "Bearer ${RD_CONSOLE_CLAUDE_TOKEN}"
      }
    }
  }
}
```

先让启动进程获得 `RD_CONSOLE_CLAUDE_TOKEN`，再运行 Claude Code 并批准这个项目 MCP。检查：

```powershell
claude mcp list
claude mcp get rd-console
```

会话中可用 `/mcp` 检查连接。[S12]

需要通过 CLI 创建项目配置时，PowerShell 可使用以下形式；单引号保留环境变量占位符，交给 Claude 读取配置时展开：

```powershell
claude mcp add --scope project --transport http rd-console http://127.0.0.1:8787/mcp --header 'Authorization: Bearer ${RD_CONSOLE_CLAUDE_TOKEN}'
```

已有同名配置时先检查并合并，不盲目重复添加或删除其他服务。也可以使用客户端提供的 user scope 做跨项目接入，但必须按实际版本验证凭证加载；项目级配置是本方案最小可复现接入方式。[S12]

### 2.4 接入后的第一条指令

```text
请连接 rd-console。
先列出我有权限访问的项目，不修改任何项目。
随后创建名为 MCP联调 的草稿项目，写入一句测试需求，
再按返回的项目ID和规格版本读取，确认写入和读取一致。
不要批准设计，不创建业务代码，不修改其他项目。
```

S1 验收后归档此测试项目，不需要把测试数据长期混在生产项目列表里。

### 2.5 代码执行的实际前提

MCP 接上控制台，不代表 AI 已进入正确代码目录。编码前必须在外部 CLI 中核对当前工作目录、仓库标识、Git 基线和授权路径。

平台知道 `repository_id=REPO-01`，不代表平台可以操作客户端的 `D:\Projects\demo`。本地项目绑定配置负责这种映射；服务端只存仓库身份和相对代码引用。

普通网页版 AI 是否可访问本机服务取决于其实际连接能力。本方案首要验证目标只承诺本地 Codex 和 Claude Code，不把其他客户端的接入写成已完成。

## 3. 角色和允许操作

| 行为 | Owner网页 | AI Client | 后续采集器 |
|---|---:|---:|---:|
| 创建/修改项目草稿 | 是 | 有范围权限时可以 | 否 |
| 写设计新修订、Task草稿、Case草稿 | 是 | 可以 | 否 |
| 请求设计评审、提出问题 | 是 | 可以 | 否 |
| 批准设计基线 | 是 | 否 | 否 |
| 授予/撤销执行授权 | 是 | 否 | 否 |
| 获取授权、启动Run | 查看/管理 | 有效授权下可以 | 仅被委派采集 |
| 提交变更、测试报告、问题 | 是 | 可以，注明来源 | 可以，注明来源 |
| 确认任务完成、人工验收 | 是 | 否 | 否 |
| 批准交付、删除历史 | 交付可；历史受保护 | 否 | 否 |

AI 读写草稿是一种低风险工作权限，不需要每保存一段文案都人工确认。它也不允许绕过已批准设计直接实施代码。

通过 `actorId`、`approvedBy` 或 `provenance=CI_VERIFIED` 等客户端自填字段，不能改变请求者权限和证据来源。身份与可信级别由服务端认证入口决定。

## 4. MCP 工具目录

工具按阶段暴露。尚未实现的工具不出现在 tools/list 中，不返回模拟成功。以下字段使用 snake_case；REST可使用既定JSON命名风格，但语义映射须唯一。

| 工具 | 阶段 | 必需输入/条件 | 返回与作用 |
|---|---|---|---|
| rd_project_list | S1 | query可选、cursor/limit | 有权限的项目摘要，不带全量设计 |
| rd_project_create | S1 | project_key、name、project_type、brief、idempotency_key | 草稿项目ID；不批准任何内容 |
| rd_outline_read | S1/S2 | project_id、scope_ref可选、cursor | 模块/Feature/阶段摘要；精确ID映射 |
| rd_spec_read | S1 | spec_id、revision_id或明确head/approved、section_ids、cursor | 正文分段、版本、哈希、未返回内容 |
| rd_spec_save | S1 | 新规格的owner/kind，或spec_id+expected_head_revision_id；正文/章节；幂等键 | 新修订ID；永不覆盖批准内容 |
| rd_plan_apply | S2 | project_id、expected_plan_version、operations、idempotency_key | 有限批量草稿写入和临时ID映射 |
| rd_review_request | S2 | target_type、target_id、candidate_version/hash | 创建待人评审项，不等于批准 |
| rd_task_context | S2/S3 | project_id、task_id或feature_id | 当前任务、批准依据、授权、限制、代码和测试入口 |
| rd_run_start | S3 | task_id、grant_id、expected_task_version、workspace_snapshot、idempotency_key | 原子领取后的run_id；重新校验授权 |
| rd_run_event | S3 | run_id、client_seq、kind、message、details | 追加阶段事件/阻塞说明；非任意状态修改 |
| rd_evidence_prepare | S3 | run_id、文件元信息、预期大小/哈希、idempotency_key | 同源限时上传目标、evidence_id、限制 |
| rd_check_record | S3/S4 | run_id、candidate_ref、profile、case_refs、status、结果和证据引用 | 技术结果记录；S3为基础报告，S4完整用例关联 |
| rd_run_submit | S3 | run_id、结果摘要、文件清单、候选版本、验证/证据/问题引用、幂等键 | SUBMITTED结果，后续任务仍未授权 |
| rd_issue_write | S2/S3 | project_id、issue_id可选、expected_version、type、影响和描述 | 创建/补充Bug、决策或变更；不直接关闭 |
| rd_history_read | S2/S3 | project_id、target_ref、cursor | 修订、评审、授权、Run、验收历史 |

### 4.1 rd_plan_apply 的边界

支持的 operation 固定为创建/更新模块草稿、Feature草稿、Task草稿和关系草稿。规格内容通过 rd_spec_save 保存，验收条目与对应规格修订一起绑定。

不得接受任意对象类型和任意字段 patch。`status=ACCEPTED`、`approved=true`、`grant.create` 等字段直接拒绝。更新已授权任务定义必须进入新的草稿/变更，不修改活跃授权快照。

默认单批最多25项和明确请求大小；关联先用temp_key，在同一事务中解析。返回 created/updated/id_mapping 和新的 plan_version。失败返回失败原因，不伪造整体完成。

### 4.2 rd_spec_save 的两种合法模式

创建：owner_ref + kind + title + markdown，expected_head为空；相同逻辑对象重复创建通过幂等键识别。

修订：spec_id + expected_head_revision_id + 新正文或受控章节替换。章节替换必须带原章节哈希；不接受“随便把第一个类似句子替换掉”的模糊操作。

每次返回新revision_id、hash、base_revision_id及保存结果。AI下一次修改必须基于该返回版本。

### 4.3 错误语义

| 错误码 | 含义 | AI动作 |
|---|---|---|
| NOT_AUTHENTICATED | 凭证缺失/无效 | 停止，不尝试猜Token |
| PROJECT_FORBIDDEN | 项目不在权限范围 | 报告，不搜索绕过 |
| VERSION_CONFLICT | 旧版本写入 | 读新版本和差异后重新提出修改 |
| EXECUTION_NOT_AUTHORIZED | 未授权代码执行 | 只报告，不自行创建授权 |
| DEPENDENCY_UNSATISFIED | 必要条件未满足 | 提问题/建议最小补齐任务 |
| BASELINE_STALE | 授权依据失效 | 停止并请求重新确认 |
| WORKSPACE_MISMATCH | 仓库/基线不匹配 | 核对本地路径，不自动reset |
| ACTIVE_RUN_EXISTS | 已有有效Run | 读取其状态，不重复执行 |
| EVIDENCE_INCOMPLETE | 缺材料/未上传完成 | 补材料，不改为通过 |
| SCOPE_VIOLATION | 业务或文件范围越界 | 提交问题，不直接推进 |
| CAPABILITY_NOT_READY | 当前版本未支持 | 不编造能力，不自动另造一套系统 |
| IDEMPOTENCY_CONFLICT | 同幂等键用于不同内容 | 改正调用逻辑，不重复写入 |

REST使用相应HTTP状态，例如401/403/409/422。MCP协议与工具错误通过SDK的规范响应表达；工具业务失败返回可解析的错误码和trace_id，不把一个字符串“ok”当成成功。HTTP认证失败应在MCP边界前拦截。

## 6. 项目绑定配置

本地仓库可以保存一份小型绑定文件，示例：

```yaml
# .rd/project.yaml：只定位，不保存动态状态
schema_version: 1
server: http://127.0.0.1:8787
project_id: PA
repository_id: REPO-01
mcp_server_name: rd-console
rules: AGENTS.md
```

不保存 Token、currentTask、approved、progress。绝对本机路径如有需要放到被 Git 忽略的 `.rd/local.yaml`，且服务器不依赖它打开文件。

允许未来同项目多个仓库；首版先支持一个主要仓库，数据结构保留repository_id。不要为了“未来多仓库”立刻实现代码同步和跨仓库提交事务。

## 7. 执行上下文示例

以下为结构示意，所有占位版本必须由服务端实际记录替换：

```yaml
schema_version: 1
project:
  id: PA
  name: 项目A
  type: WEB
feature:
  id: F-001
  name: 用户管理基础能力
  lifecycle: IMPLEMENTING
task:
  id: F-001-T02
  definition_version: 3
  name: 后端用户启停规则及测试
  state: AUTHORIZED
context:
  baseline_id: BL-008
  digest: '<上下文摘要>'
  complete: true
  required_references:
    - spec_id: SPEC-013
      revision_id: REV-007
      sections: [scope, requirements, failure-recovery, acceptance]
  omitted_required_references: []
authorization:
  grant_id: G-018
  valid_at_snapshot: true
  claim_required: true
  expires_at: '<真实有效期>'
repository:
  id: REPO-01
  expected_base_commit: '<真实代码SHA>'
allowed_paths:
  - src/modules/user/**
  - test/user/**
forbidden_paths:
  - src/ui/**
  - 'migrations/**'
  - AGENTS.md
  - CLAUDE.md
  - .rd/**
operations:
  commit: false
  push: false
  merge: false
  deploy: false
verification:
  profiles: [app-build, user-module-tests]
  acceptance_refs: [AC-U-03]
next_task:
  id: F-001-T03
  authorized: false
stop_after: SUBMIT_RESULT
```

`valid_at_snapshot` 仅表示快照当时有效；run_start 必须重新检查，防止取上下文到执行之间授权变化。不能把旧YAML当成长期通行证。

服务端实际应把必需规则正文或可按ID读取的精确引用一并返回。AI不得依据名称猜内容，也不能只读摘要就跳过明确要求的关键条款。

## 8. 两类 AI 工作流程

### 8.1 从零规划

```text
人：提出项目目标与约束
→ rd_project_list：查重和定位
→ rd_project_create：必要时建草稿项目
→ rd_spec_save：保存需求分析/架构候选/技术选择草稿
→ rd_plan_apply：创建模块、Feature和阶段草稿
→ rd_spec_save：细化当前迭代的重要功能与验收条件
→ rd_issue_write：记录真正阻塞的未决项
→ rd_review_request：提交评审
→ 停止，等待人确认
```

初期可以没有Git仓库；这不阻止需求规划。禁止因为“整个项目最终需要数据库”就先创建全部迁移和业务代码。

规划必须包含需求边界、架构理由、首版范围和可验证成果。远期模块只设计到边界，不一次生成数百页未确认实现细节。

### 8.2 已批准任务实施

```text
读本地绑定与规则
→ rd_task_context：定位唯一批准任务
→ 读取必要指定版本
→ 检查本地仓库、Git状态、工具环境
→ rd_run_start：领取有效任务
→ 用外部AI自带文件/终端工具实施
→ rd_run_event：上报关键阶段
→ 本地运行批准的验证
→ 上传必要报告/补丁/截图
→ rd_check_record：记录结果和来源
→ rd_run_submit：提交成果
→ 停止，不进入下一任务
```

没有对应任务时可以提出Task草稿，不允许自行授权后继续。项目描述中写“自动完成所有功能”也不能覆盖控制台规定的当前范围。

### 8.3 任务内修复与超范围变化

当前测试发现自身实现错误，可以在本任务批准范围内修复并再次执行测试。若需要改数据库、公共API、全局安全规则或新增未批准依赖，则上报Issue，停止相关实施。

不得为了让测试通过删除用例、降低断言、修改业务规则或把未执行标成通过。确属测试定义错误，创建设计/用例修订，等待人确认。

提交不包括 `feature_state=ACCEPTED`、`task_state=CONFIRMED`、`approved_by` 等可越权字段。下一步只是建议。

## 10. 验证配置和结果格式

任务引用批准的验证配置，配置定义在项目规格或Git中明确的权威文件。包含命令、工作目录、超时、依赖环境和报告位置。它是执行要求，不是平台远程Shell入口。

```yaml
profile_id: user-module-tests
revision: 2
repository_id: REPO-01
cwd: .
platform: windows
executable: pnpm.cmd
args: [vitest, run, test/user]
timeout_seconds: 180
expected_reports:
  - reports/vitest/*.xml
```

实际配置按项目技术栈确认。不同操作系统可有多个profile；AI不能把Windows命令直接当Linux可执行，也不能因为目标类不存在就静默换成一个容易通过的测试。

结果保存至少：profile版本、实际命令、实际cwd、代码候选、时间、退出码、测试计数、报告引用和未覆盖项。没有执行记录的状态为NOT_RUN/BLOCKED，不能凭模型推测。

CI可信来源只能由登记的CI认证入口授予。AI把普通报告文件上传过来，来源仍是AI_REPORTED。报告的哈希证明文件是否变化，不证明报告内容真实。

## 11. 大文件证据传输

不要把完整日志、截图Base64或整个仓库塞到MCP上下文。

```text
AI申请受限上传
→ 平台返回同源上传地址、evidence_id、大小/类型限制
→ AI使用本地已有文件上传能力提交真实字节
→ 服务端核对并保存
→ 上传完成后引用evidence_id写入CheckRun/Run
```

返回的地址只能指向本控制台预期origin，不允许工具参数指定任意外部回传地址。服务器不根据AI提供的本地路径读取文件。

上传和业务提交不是一个跨文件系统数据库原子事务：文件先进入暂存区，校验后标记STORED；Run只允许引用已完成证据。失败可重试；未被引用的过期暂存文件由维护任务清理。

证据访问继续按项目权限校验，不能把目录作为无鉴权静态网站暴露。敏感内容需要在本地与服务端两侧检查，不能认为哈希或HTTPS会自动脱敏。

## 12. 重试、并发和中断

| 情况 | 规则 |
|---|---|
| 写入响应丢失 | 用同幂等键重试，先确认结果是否已存在 |
| 同键内容变化 | 冲突，不返回旧成功掩盖差异 |
| 两个AI改同一设计 | 预期版本校验；后者读新版本再修订 |
| 两个AI领同一任务 | 数据库事务保证唯一有效Run |
| 两任务写同仓库 | 初版默认串行；后续再加范围冲突检测 |
| CLI中断 | 记录未完成；重开后查已有Run，不重复领取 |
| 服务中断 | 保存本地结果，停止新的受控写入；恢复后对账 |
| 授权撤销 | 不再开始/继续新的平台许可动作；已有材料可归档但不可正常推进 |
| 长时间无事件 | 显示stale/未知，不假定进程已停止或任务失败 |

MCP服务不负责强制杀死用户本地CLI进程。审批撤销不等于本地Shell已停止，界面必须把两者分开说明。

## 13. AGENTS.md 与 CLAUDE.md 的关系

共同执行规则只写一份，控制在日常可读范围。Codex通过项目AGENTS.md加载规则；Claude Code使用CLAUDE.md，并可以引用共享内容。[S02][S03]

建议：

```text

```

不要为每个功能生成一套超长Agent规则。当前范围来自task_context，不从旧规则文件推断。

工具层权限、平台审批和模型提示词各负其责。Claude官方明确区分项目说明和强制配置；本方案不把Markdown指令当安全边界。[S03]

- 可执行验收用例、所需环境和证据。
- 必要依赖和未决项。

保存新修订，说明相对已有设计的变化和影响，提交评审并停止。

## 18. 菜单管理迁移的具体示例

根据已提供正文，可以形成以下草稿映射：

| 平台内容 | 原资料对应 | 初始处理 |
|---|---|---|
| Feature | 菜单管理，旧编号P1-W01的E切片 | 显示别名，不自行认定原目录就是阶段结构 |
| 能力条目 | M-01～M-08 | 保存规则，不自动创建8个实施任务 |
| 共享引用 | API/公共规则/RBAC设计等链接 | 未读取内容标记待核实 |
| 后端设计 | 事务、安全写锁、树合法性、审计 | 保留原文及引用，不选新锁方案 |
| 前端设计 | 身份代次、动态路由、显示/停用语义 | 保留规则和来源 |
| 验收 | 原表中管理树、并发、身份竞态、故障恢复等 | 建立Case草稿，全部未执行 |
| DECISION | 关键保护入口最终清单 | 明确阻塞对应保护路径验收 |
| DEPENDENCY | B认证、C路由消费者、D角色能力 | 核验实际版本，不认定已实现 |
| 实施状态 | 原文说业务未实现 | 来源备注；真实仓库尚未核验 |

不应自动得出“Router必须在E新建”，因为原文明确涉及首个实际消费者的引入顺序。导入AI必须保留这种跨切片约束，而不是把所有关联能力都变成本Feature的新任务。

可建议的实施拆分仅作为待评审草稿：现有依赖核验、菜单后端、配置页面与既有路由整合、并发/身份/集成验证。具体拆分要读取真实仓库和关联设计后再确认。

## 19. 不允许AI自行加入的扩展

没有已批准需求时，不增加：模型聊天、模型账户管理、自主调度、插件市场、通用代码生成器、流程拖拽器、组织权限、工时、复杂报表、微服务、向量数据库、全量代码索引。

对新增设计的检查问题只有三个：

1. 它是否解决当前任务真实存在的问题？
2. 不做它是否阻止当前验收？
3. 有没有可以复用或更简单的实现？

若当前验收不需要，默认写入后续建议，不现在实现。

## 20. 推荐第一次交给AI的任务

先使用第2节启动提示词完成S0。人确认后，批准S1-T01，而不是发送“根据全部文档一次性实现完整平台”。

第一个产品里程碑应是：**本地Codex/Claude能把真实需求写进同一个控制台，网页可读取和评审版本。**随后再逐步加入任务授权、代码结果、测试和人工验收。

# AI 研发控制台：Node/TypeScript 技术实现与目录结构

版本：v1.1 · 日期：2026-09-18 · 状态：实现蓝图，尚未编码

## 1. 为什么从 Java/Spring Boot 改为 Node.js

本项目的核心负载是：项目/规格 CRUD、版本与状态事务、REST、MCP、Diff/文本处理、文件证据、SSE 和本地部署。它不是高吞吐交易系统，也没有必须依赖 Java 生态的中间件。

因此 Node.js + TypeScript 更符合首版目标：

- MCP 官方 SDK 本身就是 TypeScript 一等实现，可直接接入 Fastify。
- Web 与 Server 共用 TypeScript 类型和校验模型，减少契约重复。
- 单进程即可同时提供 REST、MCP、静态 Web 和 SSE。
- 本地自用部署可以只保留一个 Node 进程、一个 SQLite 文件和证据目录。
- 对“我 + AI / 少量开发者”的并发量，Java/Spring Boot + 独立 MySQL 服务没有必要成为默认复杂度。

保留 Java 仍然是可行方案，但在这个具体产品上没有明显收益足以抵消依赖和部署复杂度，因此 v1.1 正式改为 Node/TypeScript。

## 2. 目标运行形态

```text
开发：
Vue/Vite :5173  ──proxy──> Fastify :8787 ──> SQLite
                                  └──────> data/evidence

生产：
Browser ──> Fastify :8787
              ├── /              Vue dist
              ├── /api/v1/*      REST
              ├── /mcp           MCP Streamable HTTP
              └── /api/events    SSE（需要时）
                    │
                    ├── SQLite database
                    └── evidence directory
```

不要求 Nginx、Redis、消息队列、Docker 或对象存储才能启动。

## 3. Monorepo

```text
forgeflow/
├── apps/
│   ├── server/
│   └── web/
├── packages/
│   └── contracts/
├── migrations/
├── data/
├── docs/
├── package.json
├── pnpm-workspace.yaml
└── tsconfig.base.json
```

`packages/contracts` 只保存真正需要跨 Server/Web/MCP 共享的 Zod schema、枚举和类型。不要把所有内部实体都移入 shared package。

## 4. Server 结构

```text
apps/server/src/
├── app.ts
├── server.ts
├── config/
├── db/
│   ├── client.ts
│   └── schema/
├── modules/
│   ├── workspace/
│   │   ├── workspace.routes.ts
│   │   ├── workspace.service.ts
│   │   ├── workspace.repository.ts
│   │   └── workspace.schemas.ts
│   ├── specification/
│   ├── review/
│   ├── execution/
│   ├── quality/
│   ├── change/
│   ├── release/
│   └── security/
├── integration/
│   ├── mcp/
│   │   ├── server.ts
│   │   └── tools/
│   ├── import/
│   └── export/
└── shared/
    ├── errors/
    ├── logging/
    └── util/
```

原则：

1. `routes.ts` 只处理 HTTP、认证主体和响应格式。
2. MCP tools 只负责协议映射和输入输出，不写第二套状态机。
3. `service.ts` 是业务规则唯一入口。
4. `repository.ts` 负责 SQL/Drizzle，不决定业务状态。
5. `schemas.ts` 只放本模块实际需要的校验模型。
6. 一个简单模块可以只有 `service.ts + repository.ts`，不要为了目录整齐制造空文件。

## 5. 请求路径

```text
HTTP / MCP
   │
   ▼
Auth Context
   │
   ▼
Domain Service
   ├── policy / state transition
   ├── optimistic version check
   ├── idempotency
   └── transaction
          │
          ▼
      Repository
          │
          ▼
        SQLite
```

审批、授权、Run 启动、Run 提交这些关键写入由 Service 开启数据库事务。前端隐藏按钮不是权限控制。

## 6. 数据库

首版使用 SQLite，并开启：

```text
foreign_keys = ON
journal_mode = WAL
busy_timeout = 合理值
```

正文、Revision、Run 等普通数据写入 SQLite；截图、日志、测试报告等大文件写入 `data/evidence/`，数据库只保存元数据和 SHA-256。

推荐：Drizzle ORM + better-sqlite3。原因：Node 24 内置 `node:sqlite` 截至本稿仍是 Release Candidate；后续稳定后再评估切换。

不要：

- 把整个数据库设计成单张 JSON 表。
- 把 evidence BLOB 全部塞数据库。
- 首版同时维护 SQLite 和 MySQL/PostgreSQL。
- 声称未来数据库可以“零成本切换”；真正迁移时单独设计。

## 7. 认证

### 人类 Owner

- 初版单 Owner。
- 密码使用 Argon2id 或经评审的现代密码哈希。
- Web 登录后使用 HttpOnly Cookie Session。
- 状态写接口增加 CSRF 防护或等价同源机制。

### AI Client

- 每个 Codex/Claude 客户端签发独立高熵 Bearer Token。
- 数据库只存 Token hash、prefix、scope、project scope、过期/撤销时间。
- AI Token 永远没有 design approve、grant issue、human acceptance、delivery approve 权限。

不建设通用组织/角色/RBAC 平台。

## 8. MCP 实现

使用 MCP 官方 TypeScript SDK v2：

```text
@modelcontextprotocol/server
@modelcontextprotocol/fastify
```

Fastify 中只挂一个 MCP transport。工具函数调用和 REST 相同的 Service：

```text
rd_project_list      -> workspaceService.listProjects()
rd_spec_read         -> specificationService.getRevision()
rd_spec_save         -> specificationService.createRevision()
rd_task_context      -> executionService.getTaskContext()
rd_run_start         -> executionService.startRun()
rd_run_submit        -> executionService.submitRun()
```

MCP 工具禁止暴露：`shell_exec`、`execute_sql`、任意文件读取、任意状态设置、批准/授权接口。

## 9. Web

Vue 页面首版只做六个区域：

```text
项目总览
Feature工作台
评审中心
执行记录
版本/交付
AI接入设置
```

Feature 工作台使用 Tab，而不是每种信息独立路由成几十个页面：

```text
概览 | 设计 | 任务 | 代码/Run | 测试 | 验收 | 历史
```

设计正文仍是 Markdown，但以章节折叠、修订 Diff、待决事项和影响摘要呈现。

## 10. 实时状态

S1/S2 不需要实时通道。S3 有真实 Run 后再增加 SSE：

```text
GET /api/v1/projects/:id/events/stream
```

SSE 只推送平台已经收到的事实，例如 `RUN_STARTED / CHECK_RECORDED / RUN_SUBMITTED`。它不能伪造“AI 正在编辑第 42 行”。

## 11. 测试

Server：

- Service 单元测试：纯业务规则。
- API/MCP 接口测试：Fastify inject / SDK 客户端。
- 数据层关键事务：临时 SQLite 文件真实运行，不全部 mock。

Web：

- 关键组件和状态用 Vitest。
- 评审、授权、验收等真正重要流程用少量 Playwright E2E。

第一阶段最重要测试不是覆盖率数字，而是：

```text
Codex -> MCP 写入 revision 1
Web -> 能看到 revision 1
Claude -> MCP 读取并基于 revision 1 写 revision 2
Web -> 能看到差异
旧 revision 并发写 -> 409/业务冲突
AI 尝试批准 -> 拒绝
```

## 12. 不采用 NestJS 的原因

NestJS 可行，但首版不推荐。当前系统只有一个单体服务，没有复杂团队边界；其 Module/Controller/Provider/Decorator/DI 体系会增加 AI 自动生成模板代码的倾向。Fastify + 显式 Service/Repository 更容易控制“只写必要代码”。

以后如果项目团队和规模改变，可以重新评估，不需要把“框架偏好”升级成产品不变量。

## 13. 依赖控制

首版原则：每增加一个生产依赖必须回答“它解决了当前哪个明确问题”。建议初始集合控制在：

```text
fastify
@modelcontextprotocol/server
@modelcontextprotocol/fastify
zod
drizzle-orm
better-sqlite3
必要的 Fastify auth/cookie/static/rate-limit 插件
Vue/Vite/Element Plus
```

开发工具再加入 TypeScript、Vitest、Playwright、ESLint/Prettier 等。不要在 S1 就加入 Redis、BullMQ、Socket.IO、Prisma + Drizzle 双 ORM、GraphQL、CQRS、事件总线或微服务框架。

## 14. 数据库升级条件

SQLite 不是临时玩具，但需要明确升级触发条件。出现以下情况时再评估 PostgreSQL/MySQL：

- 多用户长期并发写成为常态。
- Run/Event 写入量使单机锁等待明显影响体验。
- 需要数据库独立高可用、远程备份/只读副本。
- 需要多个 Server 实例同时写同一数据库。

在触发前，SQLite 的单文件备份、恢复和部署简单性更符合产品目标。

## 15. 首次编码顺序

不要先生成完整目录和所有模块空文件。按 S1 创建：

```text
1. workspace 根目录 + pnpm workspace
2. Fastify 最小 server + health
3. SQLite / migration / Owner + AI token
4. project + spec revision
5. Vue 最小页面
6. MCP project/spec tools
7. 真实 Codex / Claude 联调
8. S1 验收后停止
```

S2 才创建 Feature/review/task；S3 才创建 grant/run/evidence。没有阶段需求的表和模块不提前生成。
